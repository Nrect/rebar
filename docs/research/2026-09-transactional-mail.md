# Транзакционная почта на Go: что выбрать в 2026

Дата: 2026-09-05. Всё ниже проверено по первоисточникам в этот день, а не по
памяти; где страница не открылась — так и написано. Это выводы для решения, а
не пересказ README.

## 1. Библиотека транспорта

| Библиотека | Последний релиз | Живость | CVE | Лицензия | Зависимости | Контекст/таймауты | DKIM |
|---|---|---|---|---|---|---|---|
| `wneessen/go-mail` | **v0.8.1, 2026-07-09** | активна, релизы каждые 1–2 мес | CVE-2025-59937 (smuggling через адрес, CVSS 8.2) — закрыт в 0.7.1, 2025-09 | MIT | только `x/crypto`, `x/text` | `DialAndSendWithContext`, `WithTimeout` | native с 0.8.0 |
| `jordan-wright/email` | v4.0.1, **2021-01** | мёртва | нет данных = никто не смотрит | MIT | — | нет context | нет |
| `emersion/go-smtp` (+`go-message`) | v0.25.0, 2026-08 | активна | — | MIT | — | есть | через `go-msgauth` (v0.7.0, 2025-04) |
| `xhit/go-simple-mail` | v2.16.0, **2023-08** | три года без релизов | — | MIT | `go-msgauth` | таймауты без context | есть |

**Вывод: остаёмся на go-mail.** Проект уже на v0.8.1 — это последняя версия,
уязвимость закрыта год назад, поверхность зависимостей минимальная. Ни одна
альтернатива не даёт ничего сверх: `go-smtp` — низкоуровневый клиент, MIME
пришлось бы собирать самим; остальные две не живы. Стдлибный `net/smtp`
заморожен и без STARTTLS-политик — как основа своего клиента не подходит.

DKIM: подписывать на своей стороне нужно только там, где провайдер не
подписывает сам. Postbox и Unisender Go подписывают по DNS-записям домена;
go-mail умеет подписать при необходимости, отдельная библиотека не нужна.

## 2. Outbox / очередь заданий

| Вариант | Хранилище | Последний релиз | Лицензия | Зависимости | Идемпотентность |
|---|---|---|---|---|---|
| `riverqueue/river` | Postgres | v0.47.0, 2026-08-31 | **MPL-2.0** | Go 1.26, pgx v5.10, pgerrcode, puddle, robfig/cron, gjson, sjson, x/sync + свои миграции (`river_job` и др.) | unique jobs по kind+args+period+queue+state, `InsertTx` в транзакции вызывающего, частичный уникальный индекс |
| `hibiken/asynq` | **Redis** | активна | MIT | redis | dedup по task ID |
| `vgarvardt/gue` | Postgres | v6.0.0, 2025-10 | MIT | pgx v5 или lib/pq | нет встроенной |
| свой outbox | Postgres | — | — | pgx (только в адаптере) | своя: `UNIQUE(dedup_key)` + отпечаток |

**Вывод: свой outbox.** Три причины, по убыванию веса:

1. **Переносимость.** Пакет обязан жить без pgx (ядро — stdlib + uuid, pgx
   только в адаптере). River привязывает ядро к pgx v5.10, к своим шести
   зависимостям и к своим миграциям; в проекте с `database/sql` или другим
   драйвером пакет не переносится.
2. **Наблюдаемость по соглашениям проекта.** Воркер обязан быть задачей
   `scheduler` с `cron_last_success_timestamp_seconds` — на нём стоит алерт
   «крон умер». У River свой клиент со своим циклом и своими метриками;
   впихивать его в `scheduler.Job` — обёртка ради обёртки.
3. **Размер задачи.** Три письма аутентификации. Outbox с claim/lease,
   backoff и статусами — порядка 300 строк ядра плюс адаптер. River решает
   задачу общей очереди заданий с приоритетами, периодикой, отменой; нам из
   этого нужно 10 %.

Когда River станет правильным выбором: если тулкиту понадобится общая очередь
заданий (не только письма) — тогда River как транспорт под тем же портом
`Store`, а не замена пакета. Redis ради писем — плохая сделка, asynq выбывает
на этом.

## 3. Ретраи и backoff

`cenkalti/backoff/v5` (v5.0.3, 2025-07) и `sethvargo/go-retry` уже лежат в
go.sum проекта как косвенные зависимости testcontainers. Обе хорошие. Но
формула «экспонента с полным джиттером, потолок Max» — три строки на
`math/rand/v2`, и внешняя зависимость в переносимом пакете стоит дороже трёх
строк. **Вывод: stdlib.** Библиотека не нужна.

Что действительно важно и что библиотека не решает: джиттер обязателен (после
падения провайдера все застрявшие письма иначе уходят одной волной и получают
429 той же волной), и постоянный отказ провайдера ретраить нельзя вовсе —
ретрай на MessageRejected выглядит для провайдера как спам.

## 4. Российские провайдеры транзакционной почты

Актуально на 2026-09-05. Цены с публичных страниц, могут меняться.

| Провайдер | Бесплатно | Дальше | API | Идемпотентность | Вебхуки (bounce/жалоба) | Стоп-лист | 152-ФЗ |
|---|---|---|---|---|---|---|---|
| **Yandex Cloud Postbox** | 2 000 писем/мес, бессрочно | 80,32 ₽/1000 (до 10k), 70,15 (до 50k), 59,98 дальше | **SES v2-совместимый** HTTP (`POST /v2/email/outbound-emails`, SigV4) + SMTP `postbox.cloud.yandex.net:587` STARTTLS | **нет** токена идемпотентности | **нет вебхуков.** События («принято», «доставлено», «bounce») пишутся в Cloud Logging (платно, включается флажком «Статусы писем») | **есть, автоматический**, общий на облако, с API (`Put/Get/List/DeleteSuppressedDestination`) | ЦОД в РФ, аттестован (ФСТЭК/ФСБ) |
| **Unisender Go** | 6 000/мес (500/день) **2 месяца**, потом от 800 ₽/мес | 150 ₽/1000 на младшем тарифе, 100k/мес — 5 000 ₽ по договору | свой JSON (`email/send.json`, `X-API-KEY`) + SMTP | `idempotence_key` (64 символа, **окно 1 минута**) | **есть**: delivered, soft_bounced, hard_bounced, spam, unsubscribed, opened, clicked; JSON POST, метод верификации | есть (`failed_emails.unsubscribed/blocked`) | «сервера в РФ, 152-ФЗ» на сайте |
| **SMTP.bz** | **15 000/мес бессрочно** (500/день) | 20k — 1 200 ₽/мес, 100k — 2 900 | SMTP + свой HTTP API; страница API не открылась (404) | нет данных | по отзывам есть; документацию не удалось открыть | нет данных | российская компания, ЦОД не указан |
| Rusender | 100/мес | 6k — 400 ₽/мес, 10k — 550 | SMTP + API | нет данных | не заявлены | нет данных | ЦОД в РФ (по сторонним обзорам) |
| Sendsay Транспорт | — | от 6 000 ₽/мес за 50k | API + SMTP (SMTP за доплату) | нет данных | есть | есть | РФ |
| Tendence | «месяц теста» | хостинг почты от 150 ₽/ящик | SMTP/IMAP хостинг, **не ESP** | — | — | — | Москва |

**Важные ограничения Postbox**, которые надо знать до выбора:
- квота по умолчанию **200 писем в сутки и 1 письмо в секунду** — поднимается
  заявкой в поддержку; воркер обязан держать паузу между письмами;
- без вебхуков наш собственный стоп-лист нечем кормить автоматически; но у
  Postbox стоп-лист свой и автоматический — на него можно опереться, а
  отказы видны как `MessageRejected` на отправке;
- нет токена идемпотентности — защита от дубля целиком на нашей стороне.

**152-ФЗ и трансграничная передача.** Зарубежный ESP (Mailgun, SES, Postmark)
— это трансграничная передача персональных данных: уведомление в РКН
**до начала** передачи, для стран без «адекватной защиты» (США) — ожидание
10 рабочих дней; штраф за передачу без уведомления 150–300 тыс. ₽ (ст. 13.11
КоАП). При бюджете «денег мало» единственный разумный путь — российский
провайдер.

**Вывод по провайдеру для ЛайфУрока: Postbox.**
- при текущем объёме (регистрации и сбросы, сотни в месяц) — 0 ₽; при росте
  до 10k/мес — около 640 ₽/мес;
- SES-совместимый API означает, что **один HTTP-адаптер** покрывает и Postbox
  для российских клиентов, и настоящий AWS SES для зарубежных — это главный
  аргумент для тулкита, а не для ЛайфУрока;
- Яндекс — крупнейший получатель писем учителей после Mail.ru; свой
  провайдер доставляет к себе лучше чужого;
- стоп-лист и DKIM — на их стороне, нам меньше писать.

Что теряем: вебхуки. Если понадобится собственный стоп-лист с событиями в
реальном времени — это Unisender Go (800 ₽/мес после пробного периода) и
адаптер под их JSON. Порт `Suppressor` в пакете это допускает без переделки.

SMTP.bz — самый щедрый бесплатный лимит, но проприетарный API без открытой
документации и без гарантий по вебхукам; как **SMTP-транспорт** он подходит
любому проекту тулкита без единой строки кода, и это его ниша.

## 5. Доставляемость: что обязательно, а что нет

Проверено по help.mail.ru (правила для отправителей) и требованиям Яндекса к
рассылкам; Gmail/Yahoo — по их bulk sender requirements 2024–2026.

| Требование | Mail.ru | Яндекс | Gmail/Yahoo | Для транзакционных писем ЛайфУрока |
|---|---|---|---|---|
| SPF | да | да | да | **обязательно**. Сейчас у домена `v=spf1 -all` — буквальный запрет отправки; поправить до первого письма с прода |
| DKIM | да, «используйте DKIM» | да | да | **обязательно**; ключ выдаёт провайдер, запись — в DNS |
| DMARC | «p=quarantine или p=reject» | да | да | `p=quarantine; rua=...` на старте, `reject` после недели чистых отчётов. Выравнивание: From-домен = DKIM d= = SPF-домен, значит From только с `lifeurok.ru`, не с поддомена провайдера |
| List-Unsubscribe / one-click (RFC 8058) | «валидный List-Unsubscribe» для рассылок | заголовки `Precedence: bulk`, `List-Unsubscribe` для массовых | обязателен для bulk (>5 000/день), **транзакционные освобождены** | **не ставить** на verify/reset: человек, «отписавшийся» от сброса пароля, не сможет восстановить вход. Заголовок в белом списке пакета — для уведомлений, если появятся |
| Раздельные IP/ящики для промо и транзакций | прямо требует | — | рекомендует | промо-рассылок нет; если появятся — другой From и другой провайдер/поток |
| Suppression (не слать на hard bounce) | «< 5 % невалидных адресов», иначе спам/блок | — | — | **обязательно**: у Postbox автоматический; у нас — порт `Suppressor` + отказ провайдера = `failed`, без ретраев |
| FBL / постмастер | postmaster.mail.ru | Postoffice | Postmaster Tools | завести оба после выхода на прод, это бесплатно |
| Прогрев | «постепенное увеличение объёма» | — | — | объём мал, прогрев не нужен |

Дополнительно для писем аутентификации: заголовок `Auto-Submitted:
auto-generated` (RFC 3834) — чтобы автоответчики не отвечали на «подтвердите
почту». Он в белом списке.

## 6. Двойник провайдерского API вместо Mailpit

Проверено: `POST /api/v1/send` у Mailpit принимает **свой** JSON
(`{From:{Email,Name}, To:[{Email,Name}], Subject, Text, HTML, Headers, Tags,
Attachments}` → `{ID}`); запрос сделать его SES-совместимым закрыт
мейнтейнером как *not planned* (issue #167). Значит заглушкой SES-API Mailpit
не станет.

| Вариант | Что даёт | Чего не даёт |
|---|---|---|
| Оставить SMTP в dev/stage | ноль работы | боевой HTTP-транспорт нигде не запускается до прода — недопустимо |
| `domdomegg/aws-ses-v2-local` | SES v1/v2 SendEmail (Simple/Raw/Template), `GET /store`, web-viewer, MIT | Node.js в стеке, опубликованного образа нет (собирать самим), **подпись SigV4 не проверяет** («ANY_STRING»), ошибок провайдера не имитирует |
| LocalStack SES v2 | эмуляция | SES v2 только в платных планах |
| Sandbox провайдера | настоящее поведение | у Postbox песочницы нет — есть квота 200/день и настоящие письма |
| **Свой `sesfake` в тулките** | SES v2 endpoint `POST /v2/email/outbound-emails` (Simple + Raw), проверка формы SigV4 (заголовок, подписанные заголовки, регион/сервис), возврат `MessageId`, имитация ошибок (`MessageRejected`, 429) по адресу получателя, **релей в Mailpit по SMTP** — люди читают письма там же, где привыкли | ~300 строк Go, поддерживать самим |

**Вывод: свой `sesfake`** как `mail/cmd/sesfake` в тулките с образом в ghcr.
Он же в виде `httptest.Server` (`mailtest.SESServer`) — для юнит-тестов
адаптера `sesv2` без Docker. Mailpit остаётся: он — почтовый ящик стенда, а не
провайдер. На стенде цепочка становится `backend → sesv2 → sesfake → SMTP →
Mailpit`: боевой транспорт запускается на каждом деплое стенда, а UI не
меняется.

## 7. Что НЕ нужно (коротко)

- River / gue / asynq — см. §2.
- cenkalti/backoff — см. §3.
- Отдельная DKIM-библиотека — подписывает провайдер.
- AWS SDK для SES-совместимого транспорта: SigV4 — 100 строк на stdlib, SDK
  тянет десятки модулей ради одного вызова. Своя подпись + `net/http`.
- List-Unsubscribe на письмах аутентификации.
- Redis.
