# Паттерны, которые повторяются в пакетах

Каталог механики, которой пакеты тулкита исполняют законы
[хартии корректности](CORRECTNESS.md). Хартия говорит, что обязано быть верно;
здесь — как это делается, и в каком месте оно ломается, если сделать наполовину.

Каждый паттерн описан одинаково: **когда → шаги → что обязательно проверить
тестом → пример в тулките**. Пример со ссылкой на файл — это не иллюстрация, а
образец формы: чип копирует форму и меняет содержание.

## 1. Транзакционный outbox и «enqueue только в транзакции»

**Когда.** Бизнес-факт обязан повлечь внешний эффект: письмо после
регистрации, событие после оплаты, выгрузка после импорта. Записать факт в
базу и сходить наружу — две операции, и падение между ними теряет одну из них.

**Шаги.**
1. Сборка сообщения — **чистая функция** `Prepare`: валидация, ключ дедупа,
   отпечаток. Ни хранилища, ни часов внешнего мира.
2. Вставка строки — только через `WithTx(tx)` адаптера, в транзакции
   бизнес-факта. Путь «через пул» либо отсутствует вовсе, либо документирован
   как осознанное упрощение: он честен ровно тогда, когда факт и очередь лежат
   в одной базе и падение базы одинаково ломает оба.
3. Фоновый `Run(ctx) (int, error)` берёт пачку с арендой
   (`FOR UPDATE SKIP LOCKED` + `locked_until`), увеличивая счётчик попыток.
4. Внешний вызов — **вне транзакции**, под собственным таймаутом.
5. Запись исхода — условная: `UPDATE … WHERE status = 'processing'` (и, если
   есть, `AND claim_token = $token`). Ноль строк — аренда потеряна: состояние
   не менять, пачку остановить.
6. Классификация ошибки: постоянный отказ → терминальный `failed`;
   throttling → повтор не раньше названного времени; временная и неизвестная →
   повтор по экспоненте с полным джиттером; исчерпание попыток → видимый
   dead-letter с алертом.
7. Ретеншн чистит успешные и просроченные, `failed` не трогает.

**Тест.**
- `Test*_IsAtomic`: после отката нет ни факта, ни строки очереди, ни строки
  дедупа (закон [7](CORRECTNESS.md#7-атомарность--контракт-порта-доказанный-тестом));
- гонка N воркеров: каждая строка достаётся ровно одному;
- запись исхода с устаревшим токеном аренды затрагивает ноль строк;
- **крах между эффектом и записью исхода**: дочерний процесс (тот же тестовый
  бинарь с `-test.run` и переменной окружения) делает эффект и убивает себя до
  `Finish`; родитель убеждается, что после истечения аренды строка выдаётся
  повторно с признаком «перехвачена», а идемпотентный обработчик не удваивает
  эффект;
- `Purge` не трогает `failed`.

At-least-once говорится вслух в `doc.go`: падение между эффектом и записью
исхода даёт второй эффект. Окно сужают `Lease > таймаут вызова`,
детерминированный идентификатор сообщения и политика на неизвестный исход
(повторить или отложить в ручной разбор) — но не закрывают.

**Пример.** [`mail/deliver.go`](../mail/deliver.go) (шаги 3–6),
[`mail/mailpg/claim.go`](../mail/mailpg/claim.go),
[`mail/ports.go`](../mail/ports.go) (контракты `Claim`/`Finish`),
[ADR-0001](adr/0001-mail.md#доставка). Для писем это `mail`; для доменных
событий и отложенных команд — отдельный модуль, форма та же.

## 2. Inbox для входящих событий (вебхуки)

**Когда.** Внешняя сторона доставляет события повторно by design: платёжные
провайдеры и перевозчики ретраят, пока не увидят 200. «Посмотрел, обработан ли
уже» и потом «обработал» — гонка: два ретрая, пришедшие одновременно, пройдут
проверку оба.

**Шаги.**
1. Идентификатор события детерминирован и выводится из содержимого, а не из
   времени приёма; если провайдер своего не даёт — собрать из идентификатора
   объекта и его состояния, чтобы вебхук и сверка дали один и тот же ключ.
2. Вставка отметки о приёме и бизнес-эффект — **в одной транзакции**:

   ```go
   tag, err := tx.Exec(ctx, `INSERT INTO <pkg>_events (consumer, event_id, payload_hash, received_at)
       VALUES ($1,$2,$3,$4) ON CONFLICT (consumer, event_id) DO NOTHING`, consumer, id, hash, now)
   if err != nil { return err }
   if tag.RowsAffected() == 0 { return nil } // дубль: коммитим без эффекта
   ```
3. `ON CONFLICT DO NOTHING`, а не перехват ошибки: ошибка Postgres переводит
   транзакцию потребителя в aborted целиком.
4. Отпечаток payload хранится рядом: тот же идентификатор с другим
   содержимым — конфликт, а не дубль (закон
   [3](CORRECTNESS.md#3-идемпотентность-громкая)).
5. Имя потребителя входит в ключ: одно событие законно обрабатывают разные
   подсистемы.
6. Горизонт хранения отметок ≥ окна ретраев провайдера, восстановления из
   резервной копии и ручного повтора; ретеншн — фоновая задача.
7. Ответ внешней стороне: 200 на принятое и на дубль, 400 на неразбираемое,
   503 на нашу недоступность — чтобы провайдер повторил.

**Тест.** Две параллельные транзакции с одним идентификатором: эффект ровно
один; повторная доставка после коммита — `RowsAffected == 0` и ни одного
нового эффекта; тот же идентификатор с другим payload — громкий конфликт;
ретеншн удаляет только отметки старше горизонта.

**Пример.** Формы в тулките пока нет — паттерн реализуют доменные пакеты
(платежи первыми). Механику конфликта, не роняющего чужую транзакцию,
копировать с [`mail/mailpg/enqueue.go`](../mail/mailpg/enqueue.go).

## 3. Композиция нескольких пакетов в одну транзакцию потребителя

**Когда.** Один бизнес-факт затрагивает несколько пакетов тулкита: статус
заказа, движение остатков, строка журнала, событие в очередь. Каждый из них —
отдельный модуль и ничего не знает о соседях.

**Шаги.**
1. Транзакцию открывает **потребитель**, не пакет.
2. Каждый адаптер входит в неё своим `WithTx(tx)` — единственный разрешённый
   способ; передавать `tx` в ядро запрещено, ядро транзакций не знает.
3. Порядок захвата блокировок фиксируется и документируется у потребителя.
   Тот же порядок — во всех путях кода; строки одного вида (например позиции
   по артикулу) блокируются в отсортированном порядке.
4. Внешних вызовов внутри транзакции нет (см. паттерн 4).
5. Коммит один; ошибка любого шага откатывает всё.

```go
tx, err := pool.Begin(ctx)
if err != nil { return err }
defer tx.Rollback(ctx)                     // no-op после успешного Commit
if err = orders.WithTx(tx).MarkPaid(ctx, id, now); err != nil { return err }
if err = ledger.WithTx(tx).Append(ctx, entry); err != nil { return err }
if _, err = mailStore.WithTx(tx).Enqueue(ctx, env); err != nil { return err }
return tx.Commit(ctx)
```

**Тест.** Интеграционный тест потребителя: ошибка на последнем шаге — в базе
нет ни одного из эффектов, включая строку дедупа; встречный порядок позиций в
двух параллельных транзакциях не даёт взаимной блокировки; повтор операции с
тем же ключом после успешного коммита не создаёт второй строки.

**Пример.** [`mail/README.md`, «В транзакции бизнес-факта»](../mail/README.md#отправка);
[`postgres.Runner.InTx` / `InTxRetry`](../postgres/runner.go) — если
потребитель хочет готовый идиом с таймаутами и повтором на сериализационных
ошибках; правило `WithTx` —
[CONVENTIONS §10](../CONVENTIONS.md#10-деньги-и-транзакции-у-потребителя).

## 4. Шаг саги: decide → effect → commit

**Когда.** Процесс из нескольких шагов с внешними эффектами и компенсациями:
оплата → резерв → накладная → уведомление. Отдельный пакет-оркестратор для
трёх ветвей не нужен: состояние процесса — строка заказа со статусом и
отметками шагов.

**Шаги.**
1. **Decide** — короткое чтение и **чистая функция** решения: на входе снимок
   состояния и событие, на выходе — что делать. Ни ввода-вывода, ни часов.
2. **Effect** — внешний вызов **вне транзакции** и никогда под блокировкой
   строки процесса: соединение из пула, удерживаемое на время похода к
   провайдеру, — это очередь на весь домен.
3. **Commit** — короткий CAS: `UPDATE … WHERE id = $1 AND version = $2`.
   Конфликт — не ошибка: значит, кто-то уже перевёл процесс дальше, эффекты
   были идемпотентны, событие подтверждается.
4. Идентификаторы внешних объектов **детерминированы** (`uuidv5` от
   идентификатора процесса и номера попытки): повтор шага не создаёт вторую
   накладную и второе намерение оплаты.
5. У каждой команды — идемпотентный фасад: «уже в целевом состоянии» → no-op
   с признаком «ничего не делали»; доменное событие пишет только та
   транзакция, которая реально совершила переход.
6. Таймеры не в саге: срок брони держит один пакет, срок намерения — другой;
   сага не спит и не ждёт.
7. Карта швов краха: для каждой пары «эффект — коммит» записано, что увидит
   система, если процесс умрёт между ними, и кто это чинит.
8. Компенсация — не откат: мир уже видел промежуточное состояние, поэтому
   компенсация тоже шаг со своим эффектом и своей идемпотентностью.

**Тест.** Повторная доставка каждого события — эффект ровно один; крах между
эффектом и коммитом (тот же приём с дочерним процессом, что в паттерне 1) —
после восстановления процесс доходит до конца без второго внешнего объекта;
конкурирующий коммит двух воркеров — один успех, второй видит конфликт и
подтверждает событие; чистая функция решения покрывается табличным тестом и
мутационным прогоном.

**Пример.** В тулките пока паттерн, а не пакет: пакет-оркестратор
оправдан, когда шагов больше шести с ветвящимися компенсациями или когда
появляется второй потребитель. Ближайшая по форме реализация —
`Deliver` в [`mail/deliver.go`](../mail/deliver.go): решение (`attempt`)
отделено от эффекта (`send`) и от записи исхода (`Finish`).

## 5. Клиент внешнего API

**Когда.** Пакет ходит в чужой HTTP API: платежи, доставка, почта, справочники.

**Шаги.**
1. Лимитер — на семейство методов, а не на весь клиент: у чтения и записи
   разные квоты, и общий лимитер отдаёт всё окно тому, кто чаще.
2. Ответ уважается: `Retry-After` и заголовки остатка квоты — источник паузы.
   Пауза дольше разумного потолка — не спать в задаче, а вернуть управление:
   ждать бан планировщику дешевле, чем воркеру.
3. Повтор — экспонента с **полным** джиттером и потолком, с защитой от
   переполнения сдвига: без джиттера застрявшие задачи уходят волной и
   получают отказ той же волной.
4. Ошибка классифицируется (таблица ниже), и классы объявляются **методами**,
   а не типами (`Permanent() bool`, `RetryAfter() (time.Duration, bool)`): так
   пакеты договариваются, не импортируя друг
   друга ([ADR-0005](adr/0005-packaging.md#межмодульные-зависимости-внутри-rebar-ровно-две)).
5. Пагинация отдаёт **вердикт полноты** (`исчерпано` / `упёрлись в лимит
   страниц` / `курсор не двигается`), а не просто список: «пустой 200 — не
   решение», и неполная выборка не затирает прежнюю.
6. Таймауты — только через `context`, свой на попытку; общий дедлайн операции
   выше по стеку.
7. Ни ключа, ни тела, ни токена в текстах ошибок и логах (закон
   [10](CORRECTNESS.md#10-секреты-и-персональные-данные)); подпись запроса
   считается до отправки, ответ разбирается после проверки статуса.
8. Дублёр API: `httptest`-сервер в `<pkg>test` для юнит-тестов адаптера и
   бинарь `cmd/<name>fake` для стенда — образы не публикуются.

| Класс ошибки | Что делать |
|---|---|
| временный (сеть, 5xx) | повтор по экспоненте с джиттером |
| throttling (429) | повтор не раньше `Retry-After` |
| постоянный (4xx по существу) | терминальный отказ, повторов нет |
| неоднозначный (таймаут после отправки) | повтор **с тем же ключом** либо сверка |
| потеря аренды | остановиться, состояние не менять |

Неизвестная ошибка считается временной: потерянное событие дороже лишней
попытки, а лишняя попытка безопасна ровно потому, что у операции есть ключ.

**Тест.** Таблица «код ответа → класс»; уважение `Retry-After` (включая
мусорное значение — «подсказки нет», а не ноль); распределение джиттера;
переполнение на дальних попытках даёт потолок, а не ноль; текст ошибки не
содержит ключа; вердикт полноты на оборванной пагинации; фейк отвечает так же,
как боевой, — тот же разбор.

**Пример.** [`mail/sesv2/`](../mail/sesv2) (подпись на stdlib, классификация
ответов провайдера), [`mail/mailtest/sesserver.go`](../mail/mailtest/sesserver.go)
(фейк в `httptest`), [`mail/cmd/sesfake/`](../mail/cmd/sesfake) (тот же фейк
бинарём для стенда).

## 6. Check-at-send

**Когда.** Действие отложено: письмо «оплатите» лежит в очереди, напоминание
ждёт часа отправки, задание ждёт `NotBefore`. Пока оно лежало, мир изменился —
счёт оплачен, заказ отменён, ссылка протухла.

**Шаги.**
1. Предикат «делать ли ещё» перепроверяется **в момент выполнения**, а не
   только при постановке в очередь.
2. Место для этой проверки в API обязано быть трудно не заполнить: отдельный
   шаг обработчика, а не строчка в документации.
3. Отказ по предикату — отдельный терминальный исход со своей причиной
   (`expired`, `suppressed`, «уже не нужно»), а не «успех» и не «ошибка»: на
   дашборде это разные вещи.
4. Срок жизни сообщения (`NotAfter`) — тоже предикат, и проверяется первым,
   до похода наружу.

**Тест.** Сообщение, чей предикат перестал выполняться, не уходит и получает
именно свой терминальный статус; сообщение с наступившим сроком не уходит,
даже если провайдер доступен; попытки на таких строках не тратятся впустую.

**Пример.** [`mail/deliver.go`](../mail/deliver.go), функция `attempt`:
`NotAfter` и стоп-лист проверяются до `Send`, каждый со своим исходом.
Недоступность стоп-листа даёт повтор, а не отправку, — не проверили, значит
не шлём.

## 7. Двойник вместо мока

**Когда.** Потребителю нужно тестировать свой код без Docker, а пакету —
проверять поведение ядра без адаптера.

**Шаги.**
1. Двойник **моделирует инвариант**, а не запоминает вызовы: настоящая
   уникальность ключа, настоящая аренда с истечением, настоящая
   идемпотентность.
2. Потокобезопасен: тесты идут под `-race`.
3. Инъекция отказов — полями (`Err`, `FailFor`, `RejectFor`, хук «упасть
   после эффекта»), а не подменой метода.
4. Ошибки двойника отличимы от доменных, чтобы тест не принял поломку стенда
   за штатный отказ.
5. Один и тот же контрактный набор тестов гоняется по двойнику и по
   pg-адаптеру ([CONVENTIONS §5](../CONVENTIONS.md#5-тесты)): иначе они
   разъезжаются, и тесты потребителя зелены при сломанном проде.
6. Двойник не паникует на пограничных аргументах, которые адаптер переживает
   (нулевой или отрицательный лимит выборки, пустая пачка): паника двойника
   маскируется под ошибку теста потребителя.

**Тест.** Гонка на самом двойнике; проверка, что он держит инвариант
(два `Enqueue` с одним ключом — одна строка; строка с живой арендой не
выдаётся, с истёкшей — выдаётся с признаком перехвата); контрактный набор
проходит одинаково на двойнике и на адаптере.

**Пример.** [`mail/mailtest/memstore.go`](../mail/mailtest/memstore.go)
(уникальность, аренда, стирание тела в терминальном статусе),
[`mail/mailtest/transport.go`](../mail/mailtest/transport.go),
[CONVENTIONS §3](../CONVENTIONS.md#3-двойники).

## 8. Наблюдаемость декоратором

**Когда.** Интеграцию с внешним миром обязано быть видно на дашборде, но ядро
не должно знать про OpenTelemetry.

**Шаги.**
1. Метрики — в подпакете `<pkg>otel`, декоратором **порта**: он реализует тот
   же интерфейс и вызывает вложенный.
2. Декоратор пробрасывает все методы, включая опознавательные (`Name()`):
   иначе проверки ядра «а это тот самый транспорт?» ослепнут на обёртке.
3. Метки — закрытые наборы; `result` различает `ok` / `rejected` / `error`.
4. Фоновые величины — гейджи, заполняемые **снимком**: потребитель зовёт
   `Stats` по своему расписанию и передаёт результат в `Set`. Коллбэка,
   ходящего в базу на каждый scrape, в пакете нет.
5. Имя meter — `rebar.<pkg>`; имя продукта в метрики не попадает
   ([CONVENTIONS §6](../CONVENTIONS.md#6-наблюдаемость)).
6. Таблица «метрика — тип — что» и пороги алертов живут в `doc.go` или ADR:
   метрика без записанного порога не станет алертом.

**Тест.** Метки принимают только значения из закрытого набора; `Name()`
проходит сквозь декоратор; счётчик различает три исхода на трёх видах ответа;
гейдж берёт то, что дал снимок.

**Пример.** [`mail/mailotel/transport.go`](../mail/mailotel/transport.go),
[`mail/mailotel/gauges.go`](../mail/mailotel/gauges.go),
[`scheduler/schedulerotel/observer.go`](../scheduler/schedulerotel/observer.go)
(тот же приём через порт `Observer`).

## 9. Fail-closed конфиг и подмена порта вместо флага

**Когда.** Пакет должен вести себя предсказуемо у потребителя, который его
конфигурирует впервые и половину полей не заполнит.

**Шаги.**
1. `Config` валидируется в конструкторе и **паникует**: ошибка конфигурации
   падает на старте процесса, а не на первом запросе.
2. Текст — `Config.<Поле> must …`, называющий поле и требование; связанные
   поля проверяются вместе (`Lease` больше таймаута отправки).
3. Нулевое значение — отказ, а не «выключено».
4. Флага, выключающего инвариант, нет. Режим разработки — **подмена порта**:
   двойник в тестах, явный «ненастроенный» порт в проде, где провайдера ещё
   нет.
5. «Ненастроенный» порт — не `nil` (паника у потребителя) и не логирующая
   заглушка (секреты в логах): он честно ничего не делает, очередь копится, а
   гейдж возраста и алерт показывают состояние.
6. Недоступность зависимости — `ErrUnavailable` → 503, а не «пропустим» и не
   403.

**Тест.** Табличный тест: каждое обязательное поле по отдельности роняет
конструктор с ожидаемым текстом; nil-порт — паника; с «ненастроенным» портом
фоновая задача очередь не трогает и попытки не тратит; сбой хранилища даёт
класс `unavailable`, а не «отказано».

**Пример.** [`mail/config.go`](../mail/config.go),
[`mail/unconfigured.go`](../mail/unconfigured.go),
[`kit/config`](../kit/config/config.go) (загрузка окружения: все ошибки
списком, у секретов нет умолчаний, значение редактируется при печати).

## 10. Страж импортов и белые списки по каталогам

**Когда.** Всегда: это условие переносимости. Пакет обязан компилироваться в
модуле, автора которого мы не знаем.

**Шаги.**
1. `importguard_test.go` в корне пакета разбирает импорты всех `.go` (кроме
   `_test.go`) и сверяет со **белым списком по каталогам**.
2. Путь модуля читается из `go.mod`, а не из литерала: иначе после
   копирования каталога в чужой проект страж молча разрешает всё.
3. Каталог, которого нет в списке, роняет тест: новый подпакет обязан
   объявить свои зависимости явно.
4. Ядро — stdlib и минимум (в `mail` это `uuid`); адаптер — ядро плюс ровно
   одна библиотека, ради которой он существует.
5. Вторая линия — `depguard`/`gomodguard` в конфиге линтера: pgx только в
   `*pg`, otel только в `*otel`.

**Тест.** У самого стража должен быть тест на **срабатывание**, а не только на
молчание: заведомо запрещённый импорт обязан дать находку. Страж, который
молчит всегда, выглядит точно так же, как страж, который работает, — и это уже
случалось: настройка склейки находок по строке оставляла одну находку на
строку, и запрет проигрывал соседнему правилу.

**Пример.** [`mail/importguard_test.go`](../mail/importguard_test.go)
(белый список по каталогам, путь модуля из `go.mod`);
[`kit/errs/errstest/guards.go`](../kit/errs/errstest/guards.go) — тот же приём
для запрета `http.Error` мимо единой точки ошибок, с корпусом в `testdata`,
на котором проверяется срабатывание.

## 11. Схема как контракт

**Когда.** У пакета есть pg-адаптер: `schema.sql` уезжает в миграции
потребителя и становится публичным интерфейсом наравне с портами.

**Шаги.**
1. Файл с goose-маркерами и **обеими** сторонами; потребитель копирует его как
   есть или применяет из кода строкой.
2. Пакет схему **не применяет**: `CheckSchema` на старте сверяет колонки,
   ограничения и индексы и возвращает одну ошибку со всеми расхождениями,
   первая строка — что делать. Автомиграция из библиотеки даёт две правды о
   схеме, требует DDL-прав у приложения и гонку реплик при выкате.
3. Имя таблицы — с префиксом пакета и **без имени схемы**: `search_path`
   выбирает потребитель.
4. Имена CHECK и индексов, на которые ссылается код, — контракт: адаптер
   разбирает конфликт по имени.
5. FK на таблицы потребителя нет; свои колонки потребитель добавлять вправе, и
   расхождением это не считается.
6. Закрытые enum зеркалятся CHECK; расширение — только надмножеством.
7. Время — параметром, без `DEFAULT now()` в доменных колонках.

**Тест.** Обе стороны миграции применяются на пустую базу; guard-тест
«CHECK ⊇ `All*`»; `CheckSchema` находит отсутствующий индекс, лишнюю правку
ограничения и не ругается на добавленную потребителем колонку; конфликт
распознаётся по имени ограничения, а не по коду.

**Пример.** [`mail/mailpg/schema.sql`](../mail/mailpg/schema.sql),
[`mail/mailpg/schema.go`](../mail/mailpg/schema.go),
[`mail/README.md`, «Миграция»](../mail/README.md#миграция),
[CONVENTIONS §9](../CONVENTIONS.md#9-схема-адаптера). Тесты адаптера гоняются
на базе из [`postgres/pgtest`](../postgres/pgtest/pgtest.go).

## 12. Advisory lock для тикеров (пока паттерн)

**Когда.** Периодическая задача крутится в нескольких инстансах приложения.
Планировщик тулкита — in-process: он честно запустит задачу в каждой реплике.

**Шаги.**
1. Первая линия — **идемпотентность прогона как свойство задачи**: очередь с
   арендой и `SKIP LOCKED` безопасна при любом числе воркеров, потому что
   строку берёт ровно один. Задача, устроенная так, во внешней блокировке не
   нуждается вовсе.
2. Вторая линия нужна там, где прогон не идемпотентен по построению: рассылка
   отчёта, пересчёт с усечением, выгрузка во внешнюю систему. Тогда прогон
   берёт сессионный advisory lock на своё имя и, не получив его, завершается
   без ошибки — «работает сосед», а не «сбой».
3. Ключ блокировки — из имени задачи, детерминированно; блокировка сессионная
   и снимается при падении процесса вместе с соединением.
4. Метрика последнего успеха при этом обязана считаться по тому инстансу,
   который прогон выполнил, иначе алерт «крон умер» загорится при живом кроне.

**Тест.** Два параллельных прогона одной задачи — эффект ровно один, второй
завершается без ошибки; падение держателя освобождает ключ; задача с
идемпотентным прогоном проходит тест на N воркеров без всякой блокировки.

**Пример.** Пакета пока нет: `scheduler` распределённой блокировки не имеет и
называет это в «Чего нет» — [`scheduler/doc.go`](../scheduler/doc.go);
`scheduler/pglock` намечен на v0.2, до него правило — пункт 1. Образец
идемпотентного прогона — `Claim` с арендой в
[`mail/mailpg/claim.go`](../mail/mailpg/claim.go).
