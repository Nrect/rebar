# 0010. Блок отвечает за свои гарантии, проект только поднимает версию

Статус: принято, 2026-09-15.

## Обстоятельство

rebar ведут два-три человека, а подключают его пять и больше проектов. Тяжёлые
проверки блока — контрактные наборы, `-race`, мутанты на выделенной машине —
стоят дорого, и повторять их в каждом проекте нельзя. Проекты при этом должны
оставаться тонкими: в примере-монолите клей сборки занимает 1174 строки из
2961. Готовые проверенные контракты проще и людям, и ИИ, который пишет код
проектов.

Худшие дефекты последней недели сидели не внутри блоков, а на стыках: хук
потребителя перебивал класс ошибки ядра, двойник отвечал мягче адаптера на пути
мимо ядра, трейсы уходили в коллектор без приёмника.

## Главное правило

**Дефект из-за того, как подключён блок, чинится в блоке** — умолчанием,
проверкой при старте, примером или стражем, — а не в проекте. Иначе один и тот
же дефект чинится пять раз и расходится.

## Граница: что проект проверяет сам

Тесты блока проект не гоняет: `go test ./...` зависимости и так не проверяет.
Остаются две вещи, и обе дешёвые:

1. порты, которые реализует проект (`Identities`, `Tokens`, хук `Settler`), —
   вызовом контрактного набора блока (`Run*Suite`) на своей реализации;
2. свой код — на двойниках блока. Поэтому двойник обязан вести себя как
   адаптер, и расхождение между ними — дефект блока.

## Решения

1. **Миграции едут внутри блока.** Сейчас каждый `<pkg>pg` отдаёт один
   `schema.sql`, и проект копирует его в свои миграции руками; изменение схемы
   в новой версии блока означало бы ручной `ALTER` в каждом проекте. Теперь
   адаптер экспортирует нумерованные goose-миграции через `embed`, и у каждого
   блока своя последовательность и своя таблица версий (goose v3.27:
   `NewProvider(…, fsys, WithTableName(…))`). **Применяет их раннер проекта под
   его ролью**: правило «автомиграции из библиотеки нет»
   ([ADR-0005](0005-packaging.md)) не меняется — блок везёт файлы и не
   запускает их. Переход баз, где схема уже накатана копией, решает и
   проверяет на базе монолита первый чип.
2. **Тег — гейт.** Тег ставится только после тяжёлых прогонов блока на
   выделенной машине, зелёного e2e монолита на этой версии и `lockstep`.
   `go.mod` монолита — проверенный набор версий.
3. **Dependabot в каждом проекте** на модули `github.com/nrect/rebar/*`. В самом
   rebar он уже есть вместе с еженедельным `govulncheck`, поэтому уязвимость
   закрывается одним тегом и автоматическими PR в проектах.
4. **Компилируемый пример подключения на модуль** (`example_test.go`) и рецепт
   в README модуля: когда брать, какие инварианты нельзя ломать, ссылка на
   пример. Код подключения в `doc.go` — только ссылкой на пример: проза гниёт,
   пример проверяет компилятор.
5. **Проверка при старте** — обязательный шаг подключения: `Config` уже
   паникует на негодном, `CheckSchema` сверяет базу при запуске. Ошибка сборки
   всплывает на старте, а не на трафике.

## Наблюдаемость — контракт, а не стек

Блоки говорят на стандартах и не знают, кто их слушает:

- метрики — API OpenTelemetry, наружу формат Prometheus на `/metrics` (`otelboot`);
- трейсы — OTLP, по умолчанию выключены: пустой адрес даёт noop;
- ошибки — Sentry-совместимый протокол (`errtrack`), без DSN — no-op;
- логи — через `*slog.Logger`, который передаёт проект.

Где это хранится и смотрится — Prometheus или VictoriaMetrics, Loki или
VictoriaLogs, Grafana, Sentry или GlitchTip — решает проект в своей
инфраструктуре. Смена стека блоков не касается, и стеков в rebar нет.

## Чего НЕТ

По правилу «третьего потребителя» — до тех пор, пока в него не упрётся живой
проект: слоя стандартной сборки (`wire`), HTTP-каркаса и OpenAPI, дашбордов,
генераторов проектов, DI-контейнера, новых стражей у потребителя.

## Порядок

Доделать волну [ADR-0007](0007-error-kind.md) и выпустить теги → миграции в
блоках, примеры с рецептами, Dependabot → подключить первый живой проект и
доделывать блоки по его боли.
