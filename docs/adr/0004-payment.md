# ADR-0004. Обобщение платежей: заказ, хук адаптера, провайдер без подписи

Статус: **принято** 2026-09-07 — решения владельца по карте модулей v0.1
(`payment` переезжает первым после `mail`, порт и фейк пишутся до выбора
провайдера). Форма пакета — [ADR-0001](0001-mail.md); упаковка,
схема адаптера и приёмка — [ADR-0005](0005-packaging.md).

## Контекст

Пакет платежей уже написан и работает у первого потребителя — образовательного
сервиса владельца: намерение → создание платежа у провайдера → подписанное
уведомление → одна транзакция, в которой меняется статус, дописывается книга и
выдаётся доступ → возврат → сверка с провайдером. Одиннадцать инвариантов
безопасности, страж импортов, двойники, мутационные тесты. Это лучшая по
зрелости часть кодовой базы, и она переезжает в тулкит первой.

Мешает то, что вместе с механикой денег в пакете живут правила одного проекта:
он продаёт «наборы» с проектным правилом цены, считает срок доступа в днях,
пропорционально возвращает деньги за неиспользованные дни, **запрещает**
частичный возврат по составу и сам выдаёт права внутри транзакции зачисления.

Второму потребителю — магазину на ~10 000 SKU — нужно другое: заказ вместо
набора, частичный возврат суммой, чек с позициями заказа и строкой доставки,
оплата по QR, двухстадийные платежи (холд с последующим списанием) и, главное,
боевой провайдер: у первого потребителя провайдер так и остался заглушкой.
Боевой провайдер пока не выбран, и часть рынка уведомления **не подписывает**
вовсе — проверка подлинности там устроена иначе, и это меняет главный инвариант
пакета.

## Решение в одном абзаце

Ядро остаётся тем же и худеет: предметная область первого потребителя вырезается
по закрытому списку (таблица ниже), вместо набора появляется `Reference` — строка
заказа потребителя, вместо состава — дайджест состава в отпечатке идемпотентности.
Выдача чего-либо в транзакции зачисления перестаёт быть делом ядра и становится
**хуком адаптера** `Settler`: там законны типы pgx, потому что это уже адаптер, и
именно там видна транзакция. Статус «захолдировано» вводится с первого дня, чтобы
не ломать словарь потом. Инвариант «ПОДПИСЬ ПЕРВОЙ» обобщается до **«ИСТОЧНИК
ПРАВДЫ — API ПРОВАЙДЕРА, А НЕ ТЕЛО ВЕБХУКА»**: провайдеру с подписью проверяем
подпись по сырым байтам, провайдеру без подписи — сверяем адрес отправителя со
списком и перечитываем объект у провайдера. Порт, ядро, двойники и стенд
пишутся сейчас; адаптер боевого провайдера — после выбора.

## Что вырезается и чем заменяется

Закрытый список. Всё, чего в нём нет, переезжает как есть; всё, что в нём есть,
остаётся у первого потребителя в его коде.

| Было (правило проекта) | Стало (пакет) | Почему |
|---|---|---|
| `Pack`, `PackOffer`, `PriceCart` с зашитым правилом цены, потолок наборов в корзине | `OrderItem{Position, ProductID, AmountMinor}`; котировка только **проверяется** (позиции без дыр, каждая > 0, сумма позиций = итог), потолок позиций в `Config` | правило цены принадлежит потребителю; пакет обязан лишь не дать сумме разъехаться с составом |
| `AccessDays` в намерении, пропорциональный возврат по дням | подпакет `prorate` — чистые функции без знания о намерении | срок доступа — предметная область первого потребителя, арифметика — общая |
| запрет частичного возврата по составу | снят: `RefundRequest.AmountMinor` явный, домен проверяет `0 < amount <= нетто книги` | магазин возвращает штучно; какие позиции и возвращать ли доставку — политика заказа |
| `Invalidator` (сброс чужого кэша после зачисления) | удалён; потребитель делает это после коммита по `Reason == settled` | сброс кэша — не деньги, и его сбой не должен откатывать оплату |
| `Grants`, `Revoke*`, счётчик выданного, причина «выдача сохранена» | удалены из ядра; эффекты в той же транзакции — хук адаптера `Settler` | выдача — не деньги; ядро не должно знать, что именно потребитель считает результатом оплаты |
| `ProviderName` закрытым перечислением плюс CHECK в схеме | форма `[a-z0-9_]{1,32}`, без CHECK | набор провайдеров задаёт потребитель — как набор видов писем в `mail` |
| `UserID` | `PayerID uuid.UUID` — покупатель либо гостевая корзина | магазину нужен гостевой checkout |
| `PackID` в запросе к провайдеру | убран; остаются идентификатор намерения, плательщик, сумма, валюта, описание, адрес возврата, ключ идемпотентности, чек | |
| `ParseWebhook(ctx, raw, headers)` | `ParseWebhook(ctx, WebhookRequest{Raw []byte, Headers map[string][]string, RemoteIP string})` | без подписи источником доверия становится адрес отправителя, и его нельзя не передать |
| «из обработки вебхука ни одного исходящего вызова» | «ровно один — проверочное чтение объекта у провайдера» | у провайдера без подписи это и **есть** проверка подлинности |
| сверка цен позиций с каталогом внутри создания намерения | убрана; цена считается **до** старта, пакет её не перечитывает | замороженную сделку нельзя переоценивать |

## Модель

**Намерение** — замороженная сделка:

```go
type Intent struct {
    ID uuid.UUID; PayerID uuid.UUID
    Reference string          // идентификатор заказа у потребителя
    AmountMinor int64; Currency string
    ParamsDigest []byte       // дайджест состава: сумма без состава ничего не доказывает
    Status Status; Provider string; ProviderPaymentID string
    IdempotencyKey string; Fingerprint []byte
    CreatedAt, UpdatedAt time.Time; ExpiresAt time.Time
}
```

Деньги — `AmountMinor int64` и `Currency string` по [CONVENTIONS §10](../../CONVENTIONS.md):
общего типа для денег в тулките нет, и ни одна сумма не проходит через `float64`.

**Статусы** (закрытый набор, зеркалится CHECK):
`pending → authorized → succeeded | canceled`, `pending → succeeded | canceled`.
Терминальные — `succeeded` и `canceled`, и они не воскресают: позднее уведомление
«всё ещё pending», пришедшее после зачисления, отбрасывается с меткой, а не
откатывает статус. `authorized` (деньги захолдированы, но не списаны) вводится
**с первого дня**: добавить значение в закрытый словарь, который уже лежит в
чужих CHECK и чужих алертах, — ломающее изменение (VERSIONING).

**Книга** — append-only. Зачисление — одна запись на намерение (частичный
уникальный индекс). Возврат — N встречных записей со ссылкой на зачисление;
инвариант «сумма возвратов не больше зачисления» держится двумя рубежами:
блокировкой намерения `FOR UPDATE` в транзакции и триггером на самой книге.
Один рубеж без второго — либо гонка между двумя частичными возвратами, либо
надежда на то, что все пишут в книгу только через наш код.

**События** провайдера дедуплицируются по паре `(provider, provider_event_id)` —
это inbox-приём: строка дедупа вставляется в **той же** транзакции, что и
изменение статуса, поэтому «дубль обработан наполовину» невозможен.

**Чек 54-ФЗ.** `Receipt{Customer{Email, Phone}, Items []ReceiptItem}`; достаточно
одного контакта — у покупателя часто есть только телефон. `ReceiptItem` несёт
описание, количество, сумму, код НДС, признаки предмета и способа расчёта и
необязательные код маркировки и единицу измерения: у магазина на 10 000 SKU почти
наверняка есть маркируемые категории, и добавлять поле потом означает менять
структуру, которая уже уехала к потребителям. Доставка — обычная строка чека с
признаком услуги, а не отдельное поле. `CheckReceipt` проверяет чек **до** похода
к провайдеру: отказ кассы после списания денег разбирается вручную.

**Способ оплаты и подтверждение.** `Method` (`bank_card`, `sbp`, …) передаётся
адаптеру как строка; `Confirmation{Type, URL, QRPayload}` с закрытым набором
типов (`redirect`, `qr`, `embedded`) возвращается потребителю. Оплата по QR —
это тип подтверждения, а не второй сценарий оплаты.

## Порты

```go
type Store interface {
    CreateIntent(ctx context.Context, in Intent, items []OrderItem) (CreateResult, error)
    Transition(ctx context.Context, req TransitionRequest) error
    ApplyEvent(ctx context.Context, ev Event) (ApplyResult, error)      // статус + книга + дедуп + хук — одна транзакция
    ApplyRefund(ctx context.Context, req ApplyRefundRequest) (RefundResult, error)
    StalePending(ctx context.Context, before time.Time, limit int) ([]Intent, error)
    CountStuckPending(ctx context.Context, before time.Time) (int64, error)
    Drift(ctx context.Context, since time.Time) (DriftReport, error)
}

type Provider interface {
    Name() string
    CreatePayment(ctx context.Context, req CreatePaymentRequest) (CreatePaymentResult, error)
    ParseWebhook(ctx context.Context, req WebhookRequest) (Event, error)
    GetPayment(ctx context.Context, providerPaymentID string) (Event, error)
    Refund(ctx context.Context, req RefundRequest) (Event, error)
    Capture(ctx context.Context, req CaptureRequest) (Event, error)     // ErrUnsupported у адаптеров без холдов
    Cancel(ctx context.Context, providerPaymentID, key string) (Event, error)
}
```

Ни один тип провайдера и ни один тип pgx в этих сигнатурах не появляется — это и
делает пакет копируемым (CONVENTIONS §1). `Capture` и `Cancel` объявлены сразу,
даже если первый адаптер вернёт `ErrUnsupported`: порт, который приходится
расширять, ломает всех, кто его уже реализовал.

## Хук адаптера `Settler`

```go
// paymentpg: типы pgx законны, потому что это адаптер
type Settler interface {
    OnSettled(ctx context.Context, tx pgx.Tx, in payment.Intent, items []payment.OrderItem) error
    OnRefunded(ctx context.Context, tx pgx.Tx, in payment.Intent, entry payment.LedgerEntry) error
}
```

Вызывается внутри `ApplyEvent` — после записи книги, до коммита. В нём магазин
помечает заказ оплаченным, списывает резерв и кладёт событие в `outbox`; первый
потребитель — выдаёт доступ. Ошибка хука откатывает **всё**: статус, книгу и
строку дедупа, — и ручка вебхука отвечает 503, после чего провайдер повторит
уведомление.

**Почему на уровне адаптера, а не портом ядра.** Порту ядра пришлось бы передать
транзакцию, а транзакция — это `pgx.Tx`, то есть чужой тип в ядре. Прятать её за
собственным интерфейсом бессмысленно: потребителю внутри хука нужны его же
`WithTx`-адаптеры, а они принимают `pgx.Tx`. Ядро остаётся чистым, хук живёт
там, где транзакция и так видна.

**Порядок блокировок фиксирован** и записан в `doc.go`: намерение → события →
книга → хук (внутри хука: заказ → резервы → остатки в отсортированном порядке
SKU → outbox). Порядок, зафиксированный в одном месте, — единственная защита от
взаимных блокировок между зачислением и параллельным изменением заказа.

`paymenttest.MemStore` тоже зовёт хук (без транзакции): иначе потребитель не
сможет проверить состав своей транзакции без базы.

## Источник правды — API провайдера, а не тело вебхука

Инвариант «ПОДПИСЬ ПЕРВОЙ: неподписанный запрос не должен стоить нам соединения
из пула» остаётся в силе там, где подпись есть. Часть провайдеров уведомления не
подписывает вовсе — им предписан другой порядок, и он формулируется так:

**Провайдер с подписью.** Подпись проверяется **первой**, по сырым байтам тела,
до разбора JSON и до любого обращения к базе. Тело, не прошедшее проверку, не
разбирается вовсе.

**Провайдер без подписи.**

1. `RemoteIP` сверяется со списком сетей из `Config` — **до** любого исходящего
   вызова. Пустой список — паника конструктора: dev пользуется другим
   `Provider`, а не флагом «не проверять».
2. Из тела берутся только идентификатор объекта и тип события. Всё остальное в
   теле считается недостоверным.
3. Адаптер делает **ровно один** исходящий вызов — читает объект у провайдера —
   и строит событие по ответу. Это и есть проверка подлинности: подделать чужое
   уведомление можно, подделать ответ API провайдера — нет.
4. `ProviderEventID` детерминирован и выводится из идентификатора и состояния
   объекта, а не из идентификатора уведомления. Тот же идентификатор рождается и
   при сверке, поэтому вебхук и сверка дедуплицируются друг с другом: пришли оба
   — зачисление произойдёт один раз.
5. Сбой проверочного чтения — `ErrUnavailable` → 503. Провайдеры повторяют
   уведомления сутками; отдать 200 на непроверенное событие нельзя, отдать 400
   тоже нельзя — 400 говорит «больше не повторяй».

Цена неподписанного уведомления — один исходящий HTTPS-запрос, а не соединение
из пула и не запись в базу. Дедлайн ручки вебхука у потребителя обязан быть
больше таймаута адаптера, иначе проверочное чтение будет обрываться на
полпути — это записано в чек-листе встраивания.

## Безопасность

1. **КЭША НЕТ.** Каждое решение принимается по текущему состоянию базы.
2. **ЗАЧИСЛЯЕТ ТОЛЬКО СОБЫТИЕ ПРОВАЙДЕРА** — вебхук или сверка. Возвращение
   покупателя на страницу успеха не доказывает оплату.
3. **ИСТОЧНИК ПРАВДЫ — ПОДПИСЬ ИЛИ ПЕРЕЧТЁННЫЙ ОБЪЕКТ,** и проверка делается до
   похода в базу (раздел выше).
4. **ДЕНЬГИ — ЦЕЛЫЕ МИНОРНЫЕ.** `int64`; разбор строковых сумм провайдера —
   точный, без `float64`, с fuzz-тестом на обратимость.
5. **КНИГА APPEND-ONLY.** Возврат — встречная запись, а не правка зачисления;
   сумма возвратов не больше зачисления, и это держат блокировка намерения и
   триггер книги одновременно.
6. **ИДЕМПОТЕНТНОСТЬ ГРОМКАЯ.** Ключ нормализуется в одной точке; дайджест
   состава входит в отпечаток, поэтому тот же ключ на другой состав — конфликт,
   а не тихое повторное создание.
7. **КЛЮЧ ПРОВАЙДЕРУ ПРОИЗВОДНЫЙ** от наших идентификаторов: стабилен между
   повторами одной операции и различен между разными частичными возвратами.
8. **СУММА И ВАЛЮТА ЗАМОРОЖЕНЫ В НАМЕРЕНИИ.** Расхождение с событием не
   зачисляется **ни в какую сторону** и поднимает алерт: «пришло больше» — такой
   же признак ошибки, как «пришло меньше».
9. **ТЕРМИНАЛЬНЫЕ СТАТУСЫ НЕ ВОСКРЕСАЮТ.** Запоздавшее событие о промежуточном
   состоянии отбрасывается с меткой, а не откатывает зачисление.
10. **АТОМАРНОСТЬ — КОНТРАКТ ПОРТА.** Статус, книга, строка дедупа и эффект хука
    коммитятся вместе; доказывается интеграционным тестом, в котором падение
    хука откатывает в том числе строку дедупа — иначе повтор события уже не
    применится, и деньги останутся не зачисленными навсегда.
11. **ФЛАГОВ-ВЫКЛЮЧАТЕЛЕЙ НЕТ.** Нет `SkipSignature`, нет «доверять телу», нет
    «слать синхронно»: режим разработки достигается подменой `Provider`.
12. **ЧЕК ПРОВЕРЯЕТСЯ ДО ПОХОДА К ПРОВАЙДЕРУ,** а секрет магазина не попадает ни
    в лог, ни в текст ошибки, ни в URL.

## Fail-closed для денег — что это значит

| Ситуация | Fail-open (как бывает) | Fail-closed (пакет) |
|---|---|---|
| Уведомление без подписи | тело принимается на веру | адрес отправителя из списка, затем перечтение объекта у провайдера |
| Проверочное чтение не удалось | зачисляем по телу | 503, зачисления нет, провайдер повторит |
| Сумма события ≠ сумме намерения | зачисляем «как пришло» | не зачисляем в обе стороны, метка и алерт |
| Хук потребителя упал | деньги зачислены, заказ не оплачен | откат статуса, книги и дедупа → 503 → повтор |
| Два уведомления об одном событии | двойное зачисление | дедуп `(provider, provider_event_id)` в той же транзакции |
| Возврат больше зачисления | проходит и уходит в минус | отбивается блокировкой и триггером |
| Позднее «ещё в обработке» после успеха | статус откатывается | отбрасывается с меткой |
| Заглушка провайдера в проде | флаг конфигурации | другой `Provider`; флага нет |
| Список сетей провайдера пуст | «пока без проверки» | паника конструктора |
| Намерение зависло в `pending` | висит вечно, деньги в подвешенном состоянии | сверка забирает состояние у провайдера, гейдж «зависшие» и алерт |
| Чек не собрался | платёж создан, чек не пробит | отказ до создания платежа |

## Схема (`paymentpg/schema.sql`, goose) — набросок

```sql
CREATE TABLE payment_intents (
    id                  UUID PRIMARY KEY,
    payer_id            UUID NOT NULL,
    reference           TEXT NOT NULL,
    amount_minor        BIGINT NOT NULL CHECK (amount_minor > 0),
    currency            TEXT NOT NULL CHECK (currency ~ '^[A-Z]{3}$'),
    params_digest       BYTEA NOT NULL,
    status              TEXT NOT NULL CHECK (status IN ('pending','authorized','succeeded','canceled')),
    provider            TEXT NOT NULL CHECK (provider ~ '^[a-z0-9_]{1,32}$'),
    provider_payment_id TEXT NOT NULL DEFAULT '',
    idempotency_key     TEXT NOT NULL,
    fingerprint         BYTEA NOT NULL,
    created_at          TIMESTAMPTZ NOT NULL,
    updated_at          TIMESTAMPTZ NOT NULL,
    expires_at          TIMESTAMPTZ NOT NULL
);
CREATE UNIQUE INDEX ux_payment_intents_key ON payment_intents (idempotency_key);
-- одно живое намерение на заказ: второе только после терминального первого
CREATE UNIQUE INDEX ux_payment_intents_live_reference ON payment_intents (reference)
    WHERE status IN ('pending','authorized');

CREATE TABLE payment_intent_items (
    intent_id    UUID NOT NULL REFERENCES payment_intents(id),
    position     INT  NOT NULL CHECK (position >= 0),
    product_id   TEXT NOT NULL,
    amount_minor BIGINT NOT NULL CHECK (amount_minor > 0),
    PRIMARY KEY (intent_id, position)
);

CREATE TABLE payment_events (              -- inbox: дедуп событий провайдера
    provider          TEXT NOT NULL,
    provider_event_id TEXT NOT NULL,
    intent_id         UUID NOT NULL REFERENCES payment_intents(id),
    kind              TEXT NOT NULL,
    received_at       TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (provider, provider_event_id)
);

CREATE TABLE payment_ledger (              -- append-only
    id                UUID PRIMARY KEY,
    intent_id         UUID NOT NULL REFERENCES payment_intents(id),
    kind              TEXT NOT NULL CHECK (kind IN ('capture','refund')),
    amount_minor      BIGINT NOT NULL CHECK (amount_minor > 0),
    currency          TEXT NOT NULL,
    reverses_entry_id UUID REFERENCES payment_ledger(id),
    provider_ref      TEXT NOT NULL DEFAULT '',
    created_at        TIMESTAMPTZ NOT NULL,
    CONSTRAINT payment_ledger_refund_chk CHECK ((kind = 'refund') = (reverses_entry_id IS NOT NULL))
);
-- одно зачисление на намерение
CREATE UNIQUE INDEX ux_payment_ledger_capture ON payment_ledger (intent_id) WHERE kind = 'capture';
CREATE INDEX ix_payment_ledger_reverses ON payment_ledger (reverses_entry_id) WHERE kind = 'refund';
```

Плюс два триггера, оба `ENABLE ALWAYS` — то есть работающие и под ролью
владельца схемы, и при репликации:

- **неизменяемость книги**: `UPDATE` и `DELETE` по `payment_ledger` отвергаются.
  Инвариант «append-only», который держится только дисциплиной кода, не держится
  ничем: миграция или ручная правка в проде обходят его молча;
- **потолок возвратов**: сумма возвратов по зачислению не может его превысить.
  Второй рубеж к блокировке намерения — на случай, если в книгу однажды напишут
  в обход сервиса.

Внешних ключей на таблицы потребителя нет: пакет не знает, как называется его
таблица заказов. Потребитель добавляет их своей миграцией, если хочет
(ADR-0005).

## Двойники и стенд

- `paymenttest.MemStore` — `Store` в памяти с настоящей идемпотентностью,
  книгой, дедупом событий и **вызовом хука**: потребитель проверяет состав своей
  транзакции без базы.
- `paymenttest.MemProvider` — идемпотентный по ключу провайдер с управляемыми
  исходами. Идемпотентность двойника не косметика: без неё тест «дозавершение
  после сбоя» был бы зелёным при двойном списании в проде.
- `paymenttest.ProviderServer` — `httptest.Server`, повторяющий HTTP-протокол
  провайдера: проверяет заголовок идемпотентности и авторизацию, хранит платежи,
  имитирует отказы и повторы. На нём тестируется адаптер без Docker.
- `cmd/psfake` — тот же сервер бинарём для стенда: страница «оплатить/отменить»
  и отправка уведомления на адрес потребителя. Список сетей на стенде — это
  подсеть docker, то есть значение конфигурации, а не выключатель проверки.

## Наблюдаемость и алерты

Meter — `rebar.payment`; ядро метрик не пишет (CONVENTIONS §6).

| Метрика | Тип | Что |
|---|---|---|
| `payment_provider_calls{type,result}` | counter | каждый вызов провайдера; `result` = `ok` / `rejected` (ответил определённо) / `error` (ответа нет). Сведи два последних — и алерт «провайдер недоступен» будет гореть от фонового шума |
| `payment_intents_stuck` | gauge | намерения в `pending` дольше порога — деньги в подвешенном состоянии |
| `payment_drift{kind}` | gauge | расхождения по результатам сверки |
| `cron_*{job="payments_reconcile"}` | из `scheduler` | прогоны сверки, длительность, последний успех |

Гейджи читают снимок, который потребитель обновляет после прогона сверки, а не
запросом на каждый scrape.

Алерты: «расхождение с провайдером» — `payment_drift > 0` (порог 1, разбор
обязателен); «намерения зависли» — `payment_intents_stuck > 0` пятнадцать минут;
«провайдер недоступен» — доля `result="error"` выше нескольких процентов пять
минут; «сверка умерла» — `time() - cron_last_success{job="payments_reconcile"}`
больше двух интервалов. Метка `Reason` исхода зачисления (`settled`,
`duplicate`, `already_terminal`, `amount_mismatch`, …) — закрытый набор:
её значения живут в чужих алертах, поэтому переименование ломающее.

## Чего нет (решения, не пробелы)

| Чего нет | Почему |
|---|---|
| рекуррентных платежей и сохранённых карт | нет живого запроса; хранение платёжных данных — отдельный разговор про PCI DSS |
| мультивалютности | одна валюта на намерение, конвертации нет: курс, округление и момент фиксации — предметная область, которой у нас нет |
| склада и резерва | это `inventory`; пакет не знает, что оплачивается |
| доставки и её статусов | это `delivery`; в чеке доставка — обычная строка |
| второго адаптера провайдера | до требования мерчанта: порт один, второй адаптер — три дня |
| SDK провайдеров | поверхность API мала (пять-шесть вызовов), а SDK приносит зависимости, версии и свою модель ошибок — тот же выбор, что для почтового HTTP-транспорта |
| HTTP-ручки вебхука | у потребителя: она требует его маршрутизатора, его лимитера и его формата ошибок. Правило «вебхуки живут под отдельным префиксом, а не рядом с пользовательским API» — в чек-листе встраивания |
| собственной таблицы заказов | `Reference` — строка потребителя; состав и цены считает он |

## Открыто: что нужно выяснить до адаптера

Порт, ядро, двойники и стенд от этих ответов не зависят — от них зависит только
адаптер и часть конфигурации.

| Вопрос | Что меняет |
|---|---|
| какой платёжный провайдер | какой адаптер писать; есть ли у него подпись уведомлений и холдирование |
| касса 54-ФЗ — своя облачная или у провайдера | собирается ли чек в нашем запросе или отдельным интеграционным контуром |
| есть ли маркируемые категории товаров | обязателен ли код маркировки в позициях чека |
| гостевой checkout нужен на старте | обязателен ли `PayerID` без пользователя |
| нужны ли SMS к запуску | появляется ли ещё один канал уведомлений (в тулките его нет) |
| внешняя учётная система: конфигурация и доступ к выгрузкам | появляется ли обработчик события «заказ оплачен» в очереди |

## Альтернативы

**`Pricer` портом ядра** («вторая линия: цену назначаем мы»). Отклонён: цена
считается **до** старта намерения, а замороженную сделку перепроверять нельзя —
если цена изменилась между корзиной и оплатой, правильный ответ «пересобрать
заказ», а не «пересчитать сумму в момент зачисления». Проверку состава на
непротиворечивость (позиции без дыр, сумма = итог) ядро делает и без порта.

**Выдача внутри ядра** (`Grants`, `Fulfiller` портом ядра). Отклонена: чтобы
эффект попал в ту же транзакцию, порт обязан принять транзакцию, то есть чужой
тип в ядре. Хук на уровне адаптера даёт ту же атомарность и не ломает правило
«порты без чужих типов».

**SDK провайдера вместо своего клиента.** Отклонён: пять-шесть вызовов на
stdlib против набора зависимостей с собственным жизненным циклом. То же решение
уже принято для почтового HTTP-транспорта и себя оправдало.

**Оставить `payment` у первого потребителя и написать магазину свой.** Отклонено:
это третья копия механики денег, и именно от этого уходим — разъехавшиеся копии
уже стоили нам инвариантов.

**Ждать выбора провайдера и не писать пакет.** Отклонено: от провайдера зависит
адаптер, а не порт. Ядро, двойники и стенд пишутся сейчас, и магазин может
собирать checkout на фейке.

## Решено с владельцем (2026-09-07)

1. `payment` переезжает первым после почты, вместе с `entitlement` — да.
2. Список вырезаний закрыт таблицей выше; всё остальное переезжает как есть — да.
3. Выдача уходит из ядра в хук адаптера `Settler` — да.
4. Статус «захолдировано» вводится сразу, вместе с `Capture` и `Cancel` в
   порту — да.
5. Инвариант вебхука обобщается до «источник правды — API провайдера»;
   адаптеру разрешён ровно один проверочный исходящий вызов — да.
6. Провайдер не выбран: порт, двойники и стенд пишутся сейчас, адаптер — после
   выбора провайдера — да.
7. `Pricer` портом ядра не заводится — да.

## Последствия

Плюсы: одна механика денег на двух потребителей вместо двух копий; частичные
возвраты, оплата по QR и холдирование доступны без ломающих изменений; выдача,
резервы и события живут в транзакции зачисления, но не в ядре; провайдер без
подписи обслуживается без ослабления инварианта; заглушка провайдера
физически не может оказаться в проде, потому что это другой тип, а не флаг.

Минусы, принятые осознанно: обработка неподписанного уведомления стоит одного
исходящего запроса и требует дедлайна ручки больше таймаута адаптера; хук
адаптера работает с типами pgx, то есть привязан к адаптеру Postgres (для
другой базы хук пишется заново — но и адаптер тоже); первый потребитель после
переезда несёт свои правила цены, срока и пропорционального возврата в
собственном коде — это цена того, что пакет перестал быть его частью.
