# ADR-0002. Transactional outbox для событий и команд

Статус: **принято** 2026-09-07 — решения владельца по карте модулей v0.1
(спорные вопросы про границу с `mail`, про отдельный пакет заданий и про сагу).
Форма пакета — [ADR-0001](0001-mail.md); правила упаковки, схемы адаптера и
приёмки — [ADR-0005](0005-packaging.md): ниже они не повторяются, только
применяются.

## Контекст

`mail` — частный случай общего приёма: строка коммитится вместе с бизнес-фактом,
фоновая задача забирает пачку с арендой, отдаёт транспорту, помечает исход,
повторяет с джиттером, после исчерпания попыток делает отказ видимым. Приём
общий — пакет умеет только письма.

Остальному нужно то же самое. Доменное событие: «заказ оплачен» — списать
резерв, уведомить покупателя, выгрузить во внешнюю учётную систему. Команда
внешней системе: создать накладную у перевозчика. Отложенное задание:
«освободить резерв через двадцать минут». Каждый раз это либо вызов прямо в
транзакции (и тогда внешний сбой откатывает оплату), либо вызов после коммита
(и тогда падение процесса теряет эффект). Оба проекта-потребителя, живущие с
копиями одних и тех же пакетов, такой outbox уже написали — и копии разъехались.

Исследование владельца по саге и outbox дало короткий список того, чем рабочий
outbox отличается от «своей версии за вечер»:

- enqueue **только** в транзакции факта — иначе двойная запись просто переезжает
  на шаг назад и остаётся;
- аренда с fencing-токеном — иначе воркер, проснувшийся после паузы GC, перепишет
  результат того, кто уже доделал строку;
- классификация ошибок на постоянные, временные и «повторить через N» — без неё
  постоянный отказ выжигает все попытки, а `429` не уважается;
- видимый dead-letter с аудируемым redrive — «потерялось молча» дороже отказа;
- метрика возраста старейшей просроченной строки — «очередь пуста» ничего не
  говорит о том, что воркер жив и ничего не делает.

## Решение в одном абзаце

Отдельный модуль `outbox` рядом с `mail`, форма — `mail` буквально: чистый
`Prepare`, вставка через `WithTx` адаптера, `Claim` с арендой и
`FOR UPDATE SKIP LOCKED`, `Drain(ctx) (int, error)` в сигнатуре
`scheduler.Job.Run`, `Purge`, `Stats`, двойник с настоящей арендой. Содержание —
общее: `Message` с `Kind` и непрозрачным JSON-payload, реестр хендлеров по
`Kind`, классификация ошибок по методам, dead-letter с `Redrive`, отложенный
запуск через `NotBefore`. `mail` остаётся автономным навсегда и поверх `outbox`
не переписывается. Отдельного пакета заданий нет: разовое или отложенное
задание — это `Message{NotBefore}` с хендлером, периодика — `scheduler`.

## Граница с `mail`: почему два пакета, а не один

Инварианты конфликтуют **на уровне схемы**, а не стиля:

| | `mail` | `outbox` |
|---|---|---|
| тело в терминальном статусе | обязано быть **стёрто** (CHECK `email_outbox_body_cleared_chk`): в теле ссылка с токеном | обязан **храниться** payload в `failed` — иначе redrive нечем делать |
| своё сверх общего | стоп-лист, политика `Uncertain`, `MinSendGap`, `Message-ID` | реестр хендлеров, `AggregateType/ID`, `SchemaVersion`, `Redrive` |
| адресат | ровно один, нормализуемый | нет вовсе: получатель — хендлер по `Kind` |

Одна таблица не может держать оба CHECK одновременно. Обойти это шифрованием
payload (так сделано в одном из проектов-потребителей) — значит завести ключ в
каждом потребителе и вечный ciphertext в dead-letter, который никто не сможет
прочитать глазами во время инцидента.

Общего кода — около полутора сотен строк механики (`Backoff`, нормализация
ключа, отпечаток). По [ADR-0005](0005-packaging.md) копируемые мелочи не
выносятся в общий пакет до третьего потребителя: продублировать их вместе с
тестами дешевле, чем связать два модуля релизами. Ссылка `mail` → `outbox`
означала бы, что бамп очереди двигает версию почты, и обратно.

## Модель

**Message** — то, что отдаёт потребитель: `Kind` (форма `[a-z0-9_.]{1,64}`),
`Payload json.RawMessage`, `DedupKey`, `AggregateType` и `AggregateID`,
`SchemaVersion`, `Headers`, `OccurredAt`, `NotBefore`, `NotAfter`. Payload для
пакета непрозрачен: проверяются `json.Valid` и `MaxPayloadBytes`, не содержимое.

**Envelope** — строка очереди: Message плюс `ID`, `Fingerprint`, `Status`,
`Attempts`, `AvailableAt`, `ClaimToken`, `LockedUntil`, `LastError`,
`FailReason`, времена. Плюс транзитный `Reclaimed`: ставится строке, взятой из
`processing` с истёкшей арендой; в хранилище не пишется.

**Delivery** — то, что видит хендлер: `Kind`, `Payload`, `Headers`, координаты
агрегата, `SchemaVersion`, `Attempts`, `Reclaimed`, `OccurredAt`, `NotAfter`.
Ни `ClaimToken`, ни `Store` хендлеру не видны — исход строки помечает только
`Drain`.

**Статусы** (закрытый набор, зеркалится CHECK):
`pending → processing → done | failed | expired`, `processing → pending` на
временном сбое и при отмене до старта хендлера. `FailReason` —
`permanent | exhausted`, непустой ровно у `failed`.

**Реестр.** `Registry` связывает `Kind` с `Handler`; дубль, пустой `Kind` и
`nil`-хендлер — паника конструктора, а не отказ на первой доставке.
`ErrSkip` от хендлера значит «команда устарела, эффекта нет» и даёт `done`, а
не `failed`: устаревшая команда — не отказ.

**Идемпотентность** — приём `mail`: `(kind, dedup_key)` уникален при непустом
ключе, `fingerprint` считается по содержимому сообщения. Тот же ключ и тот же
отпечаток — повтор как успех; тот же ключ и другое содержимое — `ErrKeyReused`,
громко. Ключ выводится из факта (`order_paid:<orderID>`), а не из времени.

## Порты

```go
type Store interface {   // outboxpg, outboxtest.MemStore
    Enqueue(ctx context.Context, env Envelope) (EnqueueResult, error)
    Claim(ctx context.Context, req ClaimRequest) ([]Envelope, error)
    Finish(ctx context.Context, req FinishRequest) error
    Stats(ctx context.Context, now time.Time, known []Kind) (Stats, error)
    ListFailed(ctx context.Context, limit int) ([]Envelope, error)
    Redrive(ctx context.Context, id uuid.UUID, now time.Time) (bool, error)
    Purge(ctx context.Context, before time.Time, limit int) (int, error)
}
type Producer interface {   // узкий порт для доменного кода потребителя
    Enqueue(ctx context.Context, env Envelope) (EnqueueResult, error)
}
type Handler interface { Handle(ctx context.Context, d Delivery) error }
```

Контракты, которые компилятор не проверяет, — в комментариях порта и в тестах
адаптера:

- `Enqueue` разбирает конфликт через `ON CONFLICT (kind, dedup_key) DO NOTHING`
  плюс `SELECT`, а не перехватом `23505`: ошибка Postgres переводит транзакцию
  потребителя в aborted, и законный повтор события ронял бы его бизнес-факт;
- `Claim` отдаёт только строки с `Kind` из переданного набора, берёт их
  `FOR UPDATE SKIP LOCKED`, переводит в `processing`, увеличивает `attempts`,
  пишет свой `claim_token` и возвращает прежний статус — так строка из
  `processing` приходит с `Reclaimed = true`;
- `Finish` условный: `WHERE status = 'processing' AND claim_token = $token`.
  Ноль строк — `ErrClaimLost`;
- `Purge` чистит `done` и `expired`; `failed` не трогает никогда;
- `Redrive` переводит строку **только** из `failed` в `pending`, сбрасывает
  попытки и возвращает «затронуто ли».

## Enqueue только в транзакции — на уровне типов

`mail` оставляет два пути (с транзакцией и без), потому что письмо
аутентификации честно живёт без неё. У `outbox` пути через пул нет вовсе:
событие без своего факта — это ложь потребителям события, а факт без события —
потерянный эффект. Смысл пакета в том, что этого окна нет.

```go
env, err := prod.Prepare(msg)                       // чистая валидация и отпечаток
res, err := store.WithTx(tx).Enqueue(ctx, env)      // адаптер, транзакция факта
```

`outboxpg.New(pool)` даёт значение **без** `Enqueue`: метод есть только у
результата `WithTx(tx)`. Забыть транзакцию нельзя — не соберётся. Воркеру
вставка не нужна и не должна быть доступна, поэтому он принимает узкий
интерфейс без `Enqueue`; полный `Store` реализуют `outboxtest.MemStore` и
транзакционная форма адаптера — контрактный набор тестов гоняется и по
двойнику, и по адаптеру.

## Доставка: `Drain`

`Drain(ctx) (processed int, err error)` — сигнатура `scheduler.Job.Run`:

1. `Claim`: `pending` с `available_at <= now` и `processing` с истёкшей арендой
   (эти — с `Reclaimed = true`), не более `BatchSize`, только `Kind` из реестра
   **воркера**. Попытка считается здесь, при захвате, — как в `mail`: одна
   ментальная модель на оба пакета, и падение до `Finish` не бесплатно.
2. Для каждой строки:
   - `NotAfter` наступил → `expired`;
   - хендлер под `context.WithTimeout(HandlerTimeout)` и `recover`;
   - `nil` → `done`; `ErrSkip` → `done` с меткой `skipped`;
   - ошибка с `Permanent() == true` → `failed(permanent)`, без повторов;
   - ошибка с `RetryAfter()` → повтор в `now + after`, но не дальше
     `Backoff.Max` и не позже `NotAfter`;
   - иначе `Attempts >= MaxAttempts` → `failed(exhausted)`, иначе повтор в
     `now + Backoff.Delay(attempts)` (экспонента с полным джиттером);
   - паника хендлера → как временная ошибка, метка `result="panic"`; воркер
     не падает.
   `LastError` — текст ошибки, усечённый до `MaxErrorLen` (500 байт); payload
   в него не попадает.
3. Отмена `ctx` **до** старта хендлера → `released`: строка немедленно
   возвращается в `pending`, `attempts − 1`. Быстрая остановка воркера не жжёт
   попытки. Хендлер, прерванный на середине, этого пути не получает: он
   дождётся истечения аренды и вернётся с `Reclaimed = true`.
4. `Finish` условный по `claim_token`; `ErrClaimLost` останавливает остаток
   пачки — исход, который не удалось записать, значит, что состояние строки нам
   больше не принадлежит. Исход хендлера — исход строки, а не прогона: одна
   вечно падающая строка не должна морозить гейдж последнего успеха («крон
   умер» при живом кроне). Ошибкой `Drain` являются сбой `Claim` и сбой
   `Finish`, они собираются `errors.Join`.

**Неизвестный `Kind` не забирается вовсе.** Фильтр `Claim` — реестр воркера, а
не `Config.Kinds`: при выкате новой версии старый инстанс не отправит в
dead-letter то, что умеет только новый. Такие строки видны как
`Stats.Unhandled` — гейдж и алерт, а не тишина.

`Purge(ctx) (int, error)` — вторая задача планировщика: удаляет `done` и
`expired` старше `Retention`, до `BatchSize` за вызов.

## `Config` и инварианты

`Config{Kinds, MaxAttempts, Backoff, Lease, HandlerTimeout, BatchSize, Retention, MaxPayloadBytes}`,
валидация в конструкторе, паника на негодном:

1. `Kinds` непусто, каждый по форме — метка метрики берётся отсюда, а не из
   внешнего мира.
2. `Lease > HandlerTimeout` — иначе аренда истечёт под работающим хендлером и
   вторая доставка начнётся, пока первая ещё идёт. Продления аренды нет
   осознанно (см. «Чего нет»), поэтому неравенство обязано держаться.
3. `MaxAttempts`, `BatchSize`, `MaxPayloadBytes` > 0 — нулевое значение это
   отказ, а не «без ограничения».
4. `Backoff.Max >= Backoff.Base`, `Retention > 0`.
5. Каждый `Kind` реестра ⊆ `Config.Kinds` — иначе хендлер зарегистрирован для
   того, что нельзя ни вставить, ни забрать.

## Fail-closed для очереди — что это значит

| Ситуация | Fail-open (как бывает) | Fail-closed (пакет) |
|---|---|---|
| Событие пишется после коммита факта | падение процесса теряет эффект | `Enqueue` есть только у `WithTx`: пути через пул нет |
| Неизвестный `Kind` | молча в dead-letter при выкате | не вставляется (`Prepare`) и не забирается (`Claim`); виден в `Stats.Unhandled` |
| Воркер «проснулся» после паузы GC | перезапишет исход живого воркера | `Finish` условный по `claim_token` → `ErrClaimLost` |
| Ошибка неизвестного класса | считается постоянной, событие теряется | считается временной: лишняя попытка дешевле потерянного события |
| Постоянный отказ | ретраится до исчерпания, шумит | `failed(permanent)` сразу, без повторов |
| Провайдер попросил `Retry-After` | игнорируется, лимит выжигается | повтор не раньше указанного срока |
| Dead-letter | чистится ретеншном вместе с остальным | `Purge` не трогает `failed`; payload сохранён для redrive |
| Redrive | UPDATE руками в проде | операция `Redrive` только из `failed`, актор пишется в аудит потребителя |
| Паника хендлера | падает воркер, встают все `Kind` | ошибка строки, метка `panic`, пачка продолжается |
| Nil-порт, негодный `Config` | падение на первом событии | паника на старте |

## Схема (`outboxpg/schema.sql`, goose)

Файл с маркерами `-- +goose Up` / `-- +goose Down`; ниже — тело Up.

```sql
CREATE TABLE outbox_messages (
    id              UUID PRIMARY KEY,
    kind            TEXT NOT NULL CHECK (kind ~ '^[a-z0-9_.]{1,64}$'),
    payload         JSONB NOT NULL,
    headers         JSONB NOT NULL DEFAULT '{}'::jsonb,
    aggregate_type  TEXT NOT NULL DEFAULT '',
    aggregate_id    TEXT NOT NULL DEFAULT '',
    schema_version  INT NOT NULL CHECK (schema_version > 0),
    dedup_key       TEXT NOT NULL DEFAULT '',
    fingerprint     BYTEA NOT NULL,
    status          TEXT NOT NULL CHECK (status IN ('pending','processing','done','failed','expired')),
    attempts        INT NOT NULL DEFAULT 0 CHECK (attempts >= 0),
    available_at    TIMESTAMPTZ NOT NULL,
    not_after       TIMESTAMPTZ,
    occurred_at     TIMESTAMPTZ NOT NULL,
    claim_token     UUID,
    locked_until    TIMESTAMPTZ,
    last_error      TEXT NOT NULL DEFAULT '',
    fail_reason     TEXT NOT NULL DEFAULT '' CHECK (fail_reason IN ('','permanent','exhausted')),
    created_at      TIMESTAMPTZ NOT NULL,
    updated_at      TIMESTAMPTZ NOT NULL,
    done_at         TIMESTAMPTZ,
    -- аренда существует ровно у processing: иначе «взятая» строка невидима обоим путям
    CONSTRAINT outbox_messages_claim_chk CHECK (
        (status = 'processing') = (claim_token IS NOT NULL AND locked_until IS NOT NULL)),
    CONSTRAINT outbox_messages_fail_chk CHECK ((status = 'failed') = (fail_reason <> ''))
);
-- имя индекса — часть контракта Store.Enqueue: конфликт разбирается по имени
CREATE UNIQUE INDEX ux_outbox_messages_dedup ON outbox_messages (kind, dedup_key) WHERE dedup_key <> '';
CREATE INDEX ix_outbox_messages_due ON outbox_messages (available_at, id) WHERE status IN ('pending','processing');
CREATE INDEX ix_outbox_messages_terminal ON outbox_messages (updated_at) WHERE status IN ('done','expired');
CREATE INDEX ix_outbox_messages_failed ON outbox_messages (updated_at) WHERE status = 'failed';
CREATE INDEX ix_outbox_messages_aggregate ON outbox_messages (aggregate_type, aggregate_id, occurred_at, id);
```

`kind` без списка значений в CHECK: набор задаёт потребитель, форму проверяет
регулярное выражение, принадлежность набору — `Prepare`. Правила схемы как
контракта (префикс пакета, отсутствие FK на таблицы потребителя, время
параметром, `CheckSchema` проверяет и не применяет) — [ADR-0005](0005-packaging.md)
и [CONVENTIONS §9](../../CONVENTIONS.md).

## Безопасность

1. **ENQUEUE ТОЛЬКО В ТРАНЗАКЦИИ ФАКТА.** `Prepare` + `WithTx`; «двойная
   запись» закрыта именно здесь, а не «где-то в сервисном слое».
2. **AT-LEAST-ONCE СКАЗАН ВСЛУХ.** Падение между `Handle` и `Finish` даёт
   повтор с `Reclaimed = true`; хендлер обязан быть идемпотентным — натуральный
   ключ или таблица обработанных.
3. **FENCING.** `Finish` условный по `claim_token`; ноль строк —
   `ErrClaimLost`, состояние не меняется: проснувшийся воркер не перепишет
   чужой результат.
4. **FAIL CLOSED.** Неизвестный `Kind` не вставляется и не забирается;
   nil-порт и негодный `Config` — паника на старте; `Lease > HandlerTimeout`
   проверяется там же.
5. **ИДЕМПОТЕНТНОСТЬ ГРОМКАЯ.** Тот же `(kind, dedup_key)` с другим отпечатком —
   `ErrKeyReused`, а не тихий no-op: молчание здесь прячет логическую ошибку
   потребителя.
6. **PERMANENT НЕ ПОВТОРЯЕТСЯ, THROTTLED УВАЖАЕТСЯ.** Классы — методы
   `Permanent()` и `RetryAfter()`, а не типы (ADR-0005, «структурно, а не по
   типам»). Неизвестная ошибка считается временной.
7. **DEAD-LETTER ВИДИМЫЙ И ХРАНИМЫЙ.** `failed` не чистится `Purge`, payload
   остаётся для redrive. Секреты в payload шифрует потребитель — пакет их не
   стирает и не логирует; `last_error` усечён и без payload.
8. **REDRIVE — ОПЕРАЦИЯ, НЕ SQL.** Только из `failed`, со сбросом попыток и
   ответом «затронуто ли»; актора и причину пишет аудит потребителя.
9. **МЕТКИ ЗАКРЫТЫЕ.** `kind` — из `Config.Kinds`, `result` — из набора
   исходов. `aggregate_id`, текст ошибки и payload в метки не попадают.
10. **ПАНИКА ХЕНДЛЕРА — ОШИБКА СТРОКИ.** Воркер не падает, пачка продолжается;
    отмена `ctx` останавливает пачку, взятые строки дождутся аренды.

## Чего нет (решения, не пробелы)

| Чего нет | Почему и что вместо |
|---|---|
| порядок внутри агрегата | SKIP LOCKED без FIFO — осознанно; хендлер проверяет актуальность состояния агрегата при доставке. Режим `Serial` по `ix_outbox_messages_aggregate` — v0.2, когда появится потребитель, которому порядок действительно нужен |
| LISTEN/NOTIFY-будильник | опрос через `scheduler` раз в 1–5 с проще и переживает разрыв соединения. v0.2 в `outboxpg`, если задержка станет заметной |
| продление аренды | вместо него инвариант `Lease > HandlerTimeout`: продление — второй таймер и второй способ ошибиться |
| приоритеты и несколько очередей | триггер пересмотра — см. «Альтернативы», River |
| cron-выражения | это `scheduler`; `outbox` знает только `NotBefore` |
| сага и машина состояний | отдельный пакет `saga`, когда появится второй потребитель; протокол — ниже и в [docs/PATTERNS.md](../PATTERNS.md) |
| Kafka, CDC, брокер | outbox нужен и с брокером; монолиту в одном Postgres брокер не нужен вовсе |
| шифрование payload | у потребителя: ключ его, и ciphertext в dead-letter должен быть читаем тем, у кого ключ |
| HTTP-ручки redrive | порт есть, ручка — у потребителя: она требует его аутентификации и его аудита |
| inbox для входящих вебхуков | пока паттерн, а не пакет: `ON CONFLICT DO NOTHING` в той же транзакции — [docs/PATTERNS.md](../PATTERNS.md). Пакет — при третьем потребителе |

## Заказ как сага на outbox

Пакета `saga` к старту нет, но протокол зафиксирован здесь, потому что первый
же потребитель напишет заказ, а заказ — это сага.

**Шаг саги — три части.** `decide`: короткое чтение и чистая функция, которая
по состоянию возвращает решение. `effect`: внешний эффект **вне транзакции**,
никогда под блокировкой строки заказа. `commit`: короткая транзакция с CAS по
`version` — конфликт означает, что кто-то уже применил переход, и это успех, а
не ошибка, потому что эффекты идемпотентны.

**Три слоя идемпотентности**, каждый ловит своё:

1. гарды таблицы переходов: команда, застающая заказ уже в целевом состоянии, —
   no-op, а не ошибка; доменное событие пишет только та транзакция, которая
   реально совершила переход;
2. детерминированные идентификаторы: `uuidv5(orderID + ":" + attempt)` для
   платёжного намерения и накладной — повторный вызов внешней системы с тем же
   идентификатором не создаёт вторую сущность;
3. ограничения базы: `UNIQUE` на то, что не должно повториться.

**Состояние саги — это строка заказа** (статус плюс отметки «резерв списан»,
«накладная заказана», «выгружено»), а не отдельный агрегат. Второй словарь
статусов ради трёх ветвлений не окупается.

**Таймер один и не в саге.** TTL резерва живёт у складского пакета, TTL
намерения — у платёжного, просроченное чистит `scheduler`. Сага не спит и не
ждёт.

Пакет `saga` станет оправдан, когда шагов станет больше шести с ветвящимися
компенсациями, либо появится второй потребитель, либо процесс уедет в отдельный
сервис. Тогда его извлекают из живого кода, а не пишут заранее.

## Двойники (`outboxtest`)

- `MemStore` — потокобезопасный `Store` с настоящей уникальностью
  `(kind, dedup_key)`, арендой, fencing по токену и `Reclaimed`; `Err` и
  `FinishErr` для fail-closed тестов; хук «краш между `Handle` и `Finish`».
- `RecordingHandler` — `FailFor`, `PermanentFor`, `ThrottleFor`, `PanicFor`,
  `Handled()`: каждая ветка таблицы решений `Drain` проверяется без базы.
- `Clock` — управляемые часы для TTL и backoff.

Отдельный тест доказывает то, что не доказывается двойником: дочерний процесс
забирает строку, выполняет хендлер (пишет маркер в таблицу-свидетель) и убивает
себя до `Finish`; родитель дожидается истечения аренды, получает строку с
`Reclaimed = true`, `Finish` со старым токеном не задевает ни одной строки.

## Наблюдаемость и алерты

Ядро метрик не пишет: `outboxotel.WrapRegistry` оборачивает хендлеры реестра
(CONVENTIONS §6). Meter — `rebar.outbox`.

| Метрика | Тип | Что |
|---|---|---|
| `outbox.handled{kind,result}` | counter | исход каждой доставки: `ok`, `skipped`, `retry`, `throttled`, `permanent`, `panic` |
| `outbox.handle_duration{kind}` | histogram | время хендлера; отделяет «медленно» от «падает» |
| `outbox.redrives{kind}` | counter | ручные возвраты из dead-letter |
| `outbox_pending`, `outbox_processing` | gauge | глубина очереди |
| `outbox_failed` | gauge | dead-letter до разбора |
| `outbox_unhandled` | gauge | строки с `Kind`, которого нет в реестре ни одного воркера |
| `outbox_oldest_due_age_seconds` | gauge | возраст старейшей просроченной строки |
| `cron_*{job="outbox_drain"}`, `{job="outbox_purge"}` | из `scheduler` | прогоны, длительность, последний успех |

Гейджи читают снимок `Stats`, который потребитель обновляет после каждого
прогона `Drain` (`Gauges.Set`), а не запросом в базу на каждый scrape.

Алерты: «очередь встала» — `outbox_oldest_due_age_seconds > 600` десять минут
(page); «события умирают» — `increase(outbox_failed[1h]) > 0` (порог 1, разбор
по аудиту потребителя); «есть необслуженные виды» — `outbox_unhandled > 0` пять
минут (обычно означает недокаченный выкат); «крон очереди умер» —
`time() - cron_last_success{job="outbox_drain"} > 180` при интервале 5 с.
Span доставки связывается с породившим запросом через `Headers["traceparent"]`.

## Альтернативы

**River** (планировщик заданий на Postgres). Отклонён как ядро: приваривает
пакет к своей версии pgx и своим миграциям и гоняет собственный воркер мимо
`scheduler`, из-за чего наблюдаемость «фон умер» перестаёт быть единой; в
[ADR-0005](0005-packaging.md) он остаётся допустимым адаптером за портом.
Триггеры пересмотра записаны явно: больше тысячи сообщений в минуту, приоритеты,
несколько очередей, отмена задания или потребность в готовом UI. Пока нужно
десять процентов его возможностей, а ядро — около четырёхсот строк, которые
уже написаны и покрыты тестами.

**watermill-sql и готовые pgx-outbox.** Отклонены: приносят свои таблицы,
свой словарь статусов и модель «сообщение как транспорт». Наша модель — «строка
факта», в которой dead-letter, redrive и `Stats` являются частью контракта
хранилища, а не надстройкой.

**`mail` поверх `outbox`.** Отклонено — причины в разделе «Граница с `mail`»:
конфликт CHECK по телу сообщения, разная терминология и лишняя связка релизов
ради полутора сотен общих строк.

**Отдельный пакет заданий (`jobs`).** Отклонён: разовое и отложенное задание —
это `Message{NotBefore}` с хендлером, периодика — `scheduler`. Третий словарь
статусов и второй воркер не нужны.

## Решено с владельцем (2026-09-07)

1. `mail` автономен навсегда; общий `outbox` живёт рядом по той же форме — да.
2. Отдельного модуля заданий нет; River — в «Чего нет» с триггерами пересмотра — да.
3. Пути enqueue через пул нет; `Producer` доступен только из `WithTx` — да.
4. Попытка считается при захвате (как в `mail`), а не после хендлера — да:
   одна ментальная модель на два пакета важнее экономии одной попытки.
5. Неизвестный `Kind` не забирается и виден гейджем — да; это условие
   безопасного выката в несколько инстансов.
6. Сага не пакуется до второго потребителя; протокол записан в этом ADR и в
   [docs/PATTERNS.md](../PATTERNS.md) — да.
7. Шифрование payload и HTTP-ручки redrive — у потребителя — да.

## Последствия

Плюсы: эффект, обещанный транзакцией, переживает падение процесса и провайдера;
отложенные задания не требуют второго механизма; dead-letter виден и
возвращается в работу операцией с аудитом, а не руками в проде; «фон умер»
видно одним набором алертов для почты, очереди и периодики, потому что все три
ходят через `scheduler`.

Минусы, принятые осознанно: at-least-once с известным окном — каждый хендлер
обязан быть идемпотентным, и это требование к потребителю, а не к пакету;
задержка доставки до интервала опроса; порядок внутри агрегата не гарантирован,
пока не появится режим `Serial`; полторы сотни строк механики живут в двух
копиях с `mail`, пока не найдётся третий потребитель.
