# 0011. Миграции внутри блока

Статус: принято, 2026-09-16.

Развивает [ADR-0010](0010-block-owns-guarantees.md), решение 1. Правило «своего
раннера миграций и автомиграций в библиотеке нет»
([ADR-0005](0005-packaging.md)) не меняется: блок везёт файлы, запускает их
раннер потребителя под его ролью.

## Обстоятельство

Семь адаптеров отдают по одному `schema.sql` — 457 строк на всех (`payment`
200, `auth` 56, `audit` 51, `mail` 49, `outbox` 40, `authz` 33, `entitlement`
28) и четыре триггера, три из них в `payment`. Потребитель копирует файл в свои
миграции руками. Пример-монолит держит семь таких копий
(`examples/monolith/migrations/0000N_<модуль>.sql`) плюс свою восьмую.

Раздача файлом работает ровно один раз. Изменение схемы в новой версии блока —
это ручной `ALTER` в каждом проекте: копия у потребителя ничем не связана с
файлом в блоке, и связать их нечем. `CheckSchema` расхождение находит, но
находит на старте у потребителя и после выката, а не при бампе версии.

Второй симптом — `var Schema string` у всех семи: строка со всем файлом для
того, кто применяет схему из кода. Строка задачу не решает, потому что схема —
это последовательность, а не снимок: второго файла в неё не добавить, и
«что уже применено» в ней не записано.

## Решения

### 1. Файлы: нумерованные миграции и `Migrations() fs.FS`

`<pkg>pg/migrations/00001_<pkg>_init.sql`, дальше по номеру, с маркерами
`-- +goose Up` и `-- +goose Down` — они в схемах уже есть. Экспорт:

```go
//go:embed migrations/*.sql
var migrationFiles embed.FS

// Migrations — миграции адаптера. Применяет их раннер потребителя.
func Migrations() fs.FS { … }
```

Форма — ровно та, что уже работает в `examples/monolith/migrations.go`:
проверенный образец дешевле нового.

Номер в пять знаков, а не в четыре: `goose create -s` печатает `%05v`
(`fix.go`), и монолит нумерует так же. Один формат у генератора, у примера и у
блоков — иначе страж номеров придётся учить двум.

### 2. goose блок не импортирует

Файлы — данные, `fs.FS` — stdlib, маркеры goose — комментарии SQL. Зависимости
на goose у семи модулей как не было, так и нет: она есть только у
`examples/monolith` (v3.27.3), который тегов не получает.

Причина та же, что в ADR-0005: раннер в библиотеке означает DDL-права у
приложения и гонку реплик при выкате. Блок, который раннер не импортирует, не
может его случайно запустить.

### 3. Своя последовательность и своя таблица версий

Каждый блок нумерует с 1 и ведёт свою таблицу `<pkg>_schema_version`. Одна
общая не годится: блоки выпускаются независимо, и их номера столкнутся на
первом же параллельном выпуске.

Сверено на goose v3.27.3 (пин `examples/monolith/go.mod`; последняя — v3.28.0
от 2026-09-02, `WithTableName` в ней та же). Имя задаётся опцией провайдера:

```go
func migratePayment(ctx context.Context, db *sql.DB) error {
	p, err := goose.NewProvider(goose.DialectPostgres, db, paymentpg.Migrations(),
		goose.WithTableName("payment_schema_version"))
	if err != nil {
		return err
	}
	_, err = p.Up(ctx)
	return err
}
```

Сигнатура: `NewProvider(dialect Dialect, db *sql.DB, fsys fs.FS, opts ...ProviderOption)`.
Без `WithTableName` goose пишет в `goose_db_version` — общую на все блоки.
Старый глобальный API (`goose.SetBaseFS` + `goose.UpContext`), на котором стоит
`examples/monolith/shoppg/migrate.go`, для этого не годится: состояние в нём
пакетное, семи разных таблиц у него быть не может.

Имя таблицы — по модулю, а не по префиксу таблиц: у `mail` данные лежат в
`email_outbox`, а таблица версий называется `mail_schema_version`. Потребитель
пишет это имя рядом с импортом блока, и имя модуля там — единственное, что он
знает наверняка.

Несколько реплик, стартующих разом, — забота раннера
(`goose.WithSessionLocker`, `lock.NewPostgresSessionLocker`). Блоку про это
знать нечего.

### 4. Переход баз, где схема уже накатана копией

Идемпотентная первая миграция проверена на самом тяжёлом случае —
`payment/paymentpg/schema.sql`, три триггера, PostgreSQL 16.15 (образ из
`pgtest.DefaultImage`). Правки механические: `CREATE TABLE` → `CREATE TABLE IF
NOT EXISTS`, `CREATE INDEX` → `… IF NOT EXISTS`, `CREATE FUNCTION` → `CREATE OR
REPLACE FUNCTION`, `CREATE TRIGGER` → `DROP TRIGGER IF EXISTS` + `CREATE
TRIGGER`.

**Что работает.** На пустой базе идемпотентный вариант даёт схему, совпадающую
с эталонной по `pg_constraint`, `pg_indexes` и `pg_trigger` до строки. На уже
накаченной базе он проходит в одной транзакции без ошибок.

**Где приём НЕ работает, и это решает вопрос.** `CREATE TABLE IF NOT EXISTS` на
существующей таблице пропускает тело целиком: добавленный в него CHECK не
появляется (проверено — ноль строк в `pg_constraint`). `CREATE INDEX IF NOT
EXISTS` сверяет только имя: индекс с тем же именем и другим предикатом остаётся
прежним. `ALTER TABLE … ADD CONSTRAINT IF NOT EXISTS` в Postgres нет вовсе —
синтаксическая ошибка. Идемпотентная миграция на живой базе делает вид, что
применилась, ничего не проверив.

**Ловушка, найденная по дороге.** `CREATE OR REPLACE TRIGGER` (PG 14+)
сбрасывает режим триггера с `ENABLE ALWAYS` на `ORIGIN` (`tgenabled` `A` → `O`).
Для `audit_events` и `payment_ledger` это снятая защита: append-only замолкает
на реплике — ровно там, где правят руками. Поэтому только `DROP TRIGGER IF
EXISTS` + `CREATE TRIGGER` + безусловный `ALTER TABLE … ENABLE ALWAYS TRIGGER`,
всё в одной транзакции: между DROP и COMMIT таблица под `ACCESS EXCLUSIVE`, и
окна без триггера нет.

**Решение — оба пути, в таком порядке.** Первая миграция пишется
идемпотентной: её применяют стенды, и она чинит режим триггера, если его
сбросили. Но переход живой базы закрывает не она.

1. `CheckSchema` — он единственный сверяет имена таблиц, колонок, CHECK,
   индексов и режим триггера. Красный — он называет расхождение, потребитель
   чинит своим `ALTER` и повторяет.
2. Зелёный — отметить первую миграцию применённой, не выполняя её.

Команды «отметить» у goose нет (запрос на неё — pressly/goose#938), поэтому это
два шага, оба проверены на живой базе:

```go
p, err := goose.NewProvider(goose.DialectPostgres, db, paymentpg.Migrations(),
	goose.WithTableName("payment_schema_version"))
// 1. Завести таблицу версий, не применив ничего: GetDBVersion создаёт её сам,
//    вместе с нулевой строкой.
if _, err := p.GetDBVersion(ctx); err != nil {
	return err
}
// 2. Отметить.
_, err = db.ExecContext(ctx,
	`INSERT INTO payment_schema_version (version_id, is_applied) VALUES (1, true)`)
```

После этого `p.Up(ctx)` применяет ноль миграций, и тело первой не выполняется.

**Таблицу версий руками не создавать.** goose кладёт в неё нулевую строку при
создании и на таблице без этой строки отказывается работать
(`errMissingZeroVersion`). Создаёт её goose, отметку ставит потребитель.

**Монолит.** Его `goose_db_version` останется со строками 1–7, у которых после
перехода не будет файлов. Это безопасно: goose считает неприменённое по
файловой системе, а версии из базы без файла игнорирует
(`internal/gooseutil/resolve.go`). Свой `00008_shop.sql` монолит оставляет под
тем же номером, и `Up` не находит ничего нового.

### 5. `schema.sql` удаляется

Источник правды — миграции; `schema.sql` не остаётся ни снимком, ни
генерируемым, а переезжает в `migrations/00001_<pkg>_init.sql`.

Снимок — вторая правда о схеме, то самое, против чего написан ADR-0005: в
репозитории лежал бы файл, который выглядит как то, что надо накатить, а
накатывать его нельзя. Генерируемый снимок стоит генератора и стража его
свежести, а покупает читаемость, которой у каталога из одного файла и так
довольно.

Вместе с файлом уходит `var Schema string` (есть у всех семи): строка со
снимком — тот же снимок. Это ломающее изменение API семи выпущенных модулей; по
VERSIONING на `v0.Y.Z` минорный бамп ломать API вправе, запись в CHANGELOG
обязательна.

`CheckSchema` остаётся: он сверяет имена, а не файл. Меняются его подсказки —
«скопируйте `<pkg>pg/schema.sql` в миграции» (девять мест в коде) перестают
быть верными.

Тесты адаптеров применяют схему как `pgtest.Apply(t, pool, pgtest.GooseUp(t,
"schema.sql"))` — одним файлом. Каталог одним вызовом не применяется, и это
требует помощника в `postgres/pgtest`: секции Up всех файлов по возрастанию
номера и секции Down по убыванию. Потребителей сразу семь, поэтому правило
«копия живёт до третьего потребителя» (ADR-0005) здесь не спорит.

### 6. Выпущенная миграция не правится

Файл, уехавший в теге, не меняется никогда: изменение схемы — новый файл.
Правка уехавшего и есть «изменение схемы адаптера без миграции вперёд», которое
VERSIONING называет ломающим: у того, кто первую версию уже накатил, правка не
применится никогда, и базы разойдутся молча.

Для VERSIONING одной строкой: **добавление миграции — минор**; правка
выпущенной — не патч, а расхождение баз.

### 7. Стражи, которые заводит волна

По одному на каждый способ сломать контракт.

1. **Номера не повторяются и не пропускаются** — дубль goose примет как две
   разные версии, пропуск прячет потерянный файл.
2. **В каталоге нет файла без номера** — имя, которое goose не разберёт, молча
   не применится.
3. **У каждого файла обе секции goose** — есть сегодня для `schema.sql`
   (`<pkg>pg/goose_test.go`), распространяется на каталог.
4. **Накат на пустую базу, затем Down — база пуста** — Down без пары к Up
   обнаруживается на стенде, когда он уже нужен.
5. **Накат на уже накаченную базу проходит** — проверка идемпотентности первой
   миграции; без неё она перестаёт быть идемпотентной незаметно.
6. **После наката `CheckSchema` зелёный** — иначе миграции и ожидания кода
   разъезжаются, и находит это потребитель.
7. **`tgenabled = 'A'` после наката** — у `audit` и `payment`. Наличия триггера
   мало: `CREATE OR REPLACE TRIGGER` оставляет триггер на месте и выключает его
   на реплике (решение 4).

### 8. Порядок волны

**Сначала `postgres`** — чип вне списка семи: помощники `pgtest` для наката
каталога и обратного хода. Без них семь чипов напишут семь копий одного цикла.

**Семь чипов `<pkg>pg`**, по одному на модуль, каталоги не пересекаются:
перенести `schema.sql` в `migrations/00001_<pkg>_init.sql`, сделать первую
миграцию идемпотентной, добавить `Migrations()`, убрать `Schema`, переписать
подсказки `CheckSchema`, завести стражи из решения 7, запись в CHANGELOG.
`payment` идёт первым: он самый тяжёлый (200 строк, три триггера), и на нём уже
проверены все углы.

**Чип монолита**: перестать держать копии — в `migrations/` остаётся только
`00008_shop.sql`; `Migrate` переходит с глобального API goose на `NewProvider`
с таблицей версий на блок; порядок — блоки, затем свой файл.

**Арбитру**: корневые файлы — `CONVENTIONS.md` (раздел про схему адаптера),
`VERSIONING.md` (строка про минор), `README.md`, `docs/CHECKLIST.md`,
`docs/CHIP.md`, `docs/ROADMAP.md`; бамп `postgres` и `require` на него в семи
модулях; слияние — `postgres` раньше семи, монолит последним.

Упоминаний `schema.sql` вне `.sql`-файлов сейчас 181 в 75 файлах: 58 файлов
внутри семи блоков, 3 в `postgres`, 1 в `examples`, 13 в корне и `docs/`.
Старый совет живёт в `doc.go`, комментариях, README модулей и CHANGELOG —
каждому чипу грепать свой каталог, а не только править код.

## Чего НЕТ

- **Раннера миграций в библиотеке.** DDL-права у приложения и гонка реплик при
  выкате — цена потребителя, а не блока (ADR-0005).
- **Автомиграций на старте.** Две правды о схеме: код и миграции спорят, кто
  главный. `CheckSchema` сверяет и не меняет — это и есть ответ.
- **Зависимости на goose.** Блок везёт файлы; маркеры goose — комментарии SQL,
  и раннер потребителя может быть не goose.
- **Генератора схемы из кода.** Имена CHECK и индексов — контракт, и
  придумывать их генератору нельзя.
- **Отката в проде по кнопке.** Секция Down есть и проверяется тестом, но
  `Down` на живой базе — потеря данных под видом операции. Откат выпущенной
  схемы — новая миграция вперёд.

## Последствия

Плюсы: изменение схемы едет бампом версии, а не ручным `ALTER` в каждом
проекте; «что накачено» записано в базе, а не в голове; расхождение находит
`CheckSchema` на старте, а не первая упавшая вставка.

Минусы, принятые осознанно:

- у потребителя семь таблиц версий вместо одной и семь вызовов раннера вместо
  одного цикла;
- первая миграция идемпотентна, а значит на существующей таблице ничего не
  проверяет (решение 4); проверяет `CheckSchema`;
- `Schema` убирается у семи выпущенных модулей — минорный бамп, ломающий сборку
  тем, кто его звал;
- волна двигает `postgres` и `require` на него в семи модулях, то есть
  `lockstep` и восемь бампов одним заходом.

## Порядок работ

`postgres` (помощники `pgtest`) → семь `<pkg>pg`, начиная с `payment` → монолит
→ корневые файлы и бампы у арбитра. Теги — по ADR-0010, решение 2: после
тяжёлых прогонов блока на выделенной машине и зелёного монолита на этой версии.
