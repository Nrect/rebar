# ADR-0003. Три оси доступа: `auth`, `authz`, `entitlement`

Статус: **принято** 2026-09-07 — решения владельца по карте модулей v0.1
(один модуль `auth`, минимальный RBAC своими силами, `entitlement` отдельно).
Форма пакета — [ADR-0001](0001-mail.md); упаковка, схема адаптера и приёмка —
[ADR-0005](0005-packaging.md).

## Контекст

В проектах-потребителях аутентификация написана дважды и копии разъехались: в
одном зрелее защита от перебора и ограничение одновременных хэширований, в
другом — форма пакета (страж импортов, двойники, `SetClock`). Роли лежат
колонкой в таблице пользователей и проверяются условиями по коду; список
операций, которые вообще требуют проверки, нигде не записан, поэтому забытая
проверка выглядит как обычный хендлер. Права на купленный объект в
образовательном сервисе владельца сделаны отдельным пакетом с кэшем и
default-deny — и это единственная из трёх частей, которая уже сегодня в
правильной форме.

Магазину через месяц нужны вход, роли персонала и гостевой checkout; первому
потребителю — переезд без потери его инвариантов. Написать это одним пакетом
«авторизация» соблазнительно и неправильно: смешиваются три разных вопроса.

| Вопрос | Пакет | Кто отвечает | Срок жизни ответа |
|---|---|---|---|
| кто ты | `auth` | сессия и пароль | до истечения сессии |
| вправе ли ты делать это | `authz` | роли и разрешения | до отзыва роли, читается каждый раз |
| что тебе открыто по покупке | `entitlement` | выдача с датой окончания | до `expires_at`, кэшируется с дедлайном |

Слить их — значит притащить кэш и сроки покупки в проверку ролей, а отзыв роли
сделать медленным, потому что он поедет по чужому TTL.

## Решение в одном абзаце

Три модуля. `auth` — один модуль с пакетами (`password`, `session`, адаптеры),
а не три ради шести общих типов; реалм — это экземпляр `session.Service` со
своим секретом, кукой и источником личностей; сессии непрозрачные, со
скользящим `IdleTTL` и абсолютным `SessionTTL`; ни JWT, ни refresh-токенов, ни
ролей. `authz` — минимальный RBAC: субъект → роли (источник ролей — порт у
потребителя) → разрешения (закрытый набор в `Config`), наследование ролей,
реестр операций с default-deny и инвариант-тестом, хук `Policy`, который может
только сужать. `entitlement` переезжает как есть с переименованиями и остаётся
отдельной осью; `authz.Policy` — штатная точка его подключения.

Помощники для токенов (генерация, HMAC, тип секрета) лежат в корне `auth`, а не
отдельным пакетом: их три функции, и они нужны и `session`, и потребителю,
который реализует порт `Tokens`. `auth/authhttp` — одна из двух разрешённых
межмодульных зависимостей (`kit/httperr`), см. [ADR-0005](0005-packaging.md).

## `auth`: модель и порты

**Реалм — это экземпляр сервиса.** Два реалма (покупатели и персонал)
различаются секретом, кукой и таблицей личностей — то есть конфигурацией, а не
кодом. Общим остаётся один `password.Hasher` на процесс: потолок
одновременности должен быть общим, иначе два реалма сложат свои лимиты памяти.

```go
type Realm string     // [a-z0-9_]{1,32}
type Principal struct { Realm Realm; SubjectID uuid.UUID; SessionHash string }
type Identity  struct { ID uuid.UUID; Login, PasswordHash string; Verified, Disabled bool }

type Identities interface {   // таблица пользователей — у потребителя
    ByLogin(ctx context.Context, login string) (Identity, error)   // ErrIdentityNotFound
    ByID(ctx context.Context, id uuid.UUID) (Identity, error)
    Create(ctx context.Context, login, passwordHash string, at time.Time) (uuid.UUID, error)
    SetPasswordHash(ctx context.Context, id uuid.UUID, hash string, at time.Time) error
}
```

Таблицы пользователей в пакете нет и не будет: у каждого потребителя свой
профиль, свои связи и свои внешние ключи. `Create` возвращает `ErrLoginTaken`,
разобранный по **имени** уникального индекса, а не по SQLSTATE — правило
[CONVENTIONS §9](../../CONVENTIONS.md).

**`password`.** `Hasher` считает argon2id и отдаёт PHC-строку с параметрами
внутри; при проверке параметры ограничены сверху — враждебный хэш, попавший в
базу, не заставит процесс выделить гигабайт. `Hash` и `Verify` проходят через
глобальный семафор на 2–4 слота: память — свойство одновременности, и лимитер
по IP её не режет. Переполнение даёт `ErrBusy`, который не оборачивает
`context.DeadlineExceeded` (иначе `errors.Is` в HTTP-слое превратил бы отказ по
занятости в таймаут). `Policy` — длина и оценка стойкости через порт
`StrengthChecker`; порог оценки считается по префиксу в 64 байта, потому что
алгоритм квадратичный по длине.

**`session`.** Порты:

```go
type Sessions interface { Create; Get; Touch; Delete; DeleteOfSubject; Purge }   // authpg готов
type Attempts interface { CountSince; Record; Clear; Purge }                     // authpg готов
type Tokens interface {                                                          // РЕАЛИЗУЕТ ПОТРЕБИТЕЛЬ
    Issue(ctx context.Context, t OneTimeToken, n Notification) error
    Consume(ctx context.Context, req ConsumeRequest) (uuid.UUID, error)
}
type Notifier interface { Notify(ctx context.Context, n Notification) error }
type Auditor  interface { Record(ctx context.Context, ev Event) error }          // nil допустим
```

Сценарии сервиса: `Register` (семантика «принято», а не «создано»), `SignIn`
(`ErrInvalidCredentials | ErrTooManyAttempts | ErrNotVerified`), `Resolve`
(скользящее продление не чаще `RenewEvery`), `SignOut` и `SignOutAll`,
`ChangePassword` (с отзывом всех сессий и всех токенов сброса),
`Request/Confirm` для подтверждения адреса, сброса пароля и смены логина,
`Sweep(ctx) (int, error)` в сигнатуре `scheduler.Job.Run`, `SetClock`.

### Почему `Tokens` реализует потребитель

Это единственный порт, для которого пакет **не** даёт готовой реализации, и
причина в атомарности.

`Consume` обязан одной транзакцией погасить токен (таблица пакета) **и**
применить эффект в таблице пользователей (таблица потребителя): подтвердить
адрес, записать новый хэш пароля, сменить логин. `Issue` обязан одной
транзакцией погасить прежние токены того же назначения, вставить новый и
поставить письмо в очередь (`mail.Prepare` + `mailpg.WithTx`). Пакет не владеет
обеими таблицами и транзакции в контексте не носит (ADR-0001), поэтому
атомарность живёт там, где обе таблицы видны, — у адаптера потребителя.

Пакет даёт его половину: `authpg` отдаёт `WithTx(tx).Insert`,
`RevokeOfSubject`, `ConsumeRow` на `Querier`. Адаптер потребителя — около
двадцати пяти строк поверх `postgres.Runner`. Контракт «в одной транзакции»
держится интеграционным тестом адаптера — как `Test*_IsAtomic` в остальных
пакетах (CONVENTIONS §5).

### `Config` и инварианты

`Config{Realm, Secret, SessionTTL, IdleTTL, RenewEvery, LockoutAttempts, LockoutWindow, VerifyTTL, ResetTTL, EmailChangeTTL, AllowUnverifiedSignIn}`,
паника конструктора на негодном:

1. `Realm` по форме, `Secret` не короче 32 байт — HMAC под коротким секретом
   создаёт видимость защиты токенов.
2. `0 < IdleTTL <= SessionTTL` — скользящий срок не может пережить абсолютный.
3. `0 < RenewEvery < IdleTTL` — иначе продление либо не срабатывает, либо
   пишет в базу на каждый запрос.
4. `LockoutAttempts > 0` и все TTL > 0 — нулевое значение здесь означало бы
   «без ограничения», то есть fail-open.
5. `ResetTTL <= 1h`, `VerifyTTL <= 72h` — потолки против абсурда в конфиге
   потребителя; ссылка сброса, живущая неделю, — это не настройка, а ошибка.
6. `AllowUnverifiedSignIn` по умолчанию `false`: нулевое значение — строгая
   регистрация.

### Схема (`authpg/schema.sql`)

Три таблицы, `realm` в каждой строке и в каждом `WHERE`:

```sql
CREATE TABLE auth_sessions (
    token_hash      TEXT PRIMARY KEY,          -- HMAC, не сырой токен
    realm           TEXT NOT NULL CHECK (realm ~ '^[a-z0-9_]{1,32}$'),
    subject_id      UUID NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL,
    last_seen_at    TIMESTAMPTZ NOT NULL,
    expires_at      TIMESTAMPTZ NOT NULL,
    idle_expires_at TIMESTAMPTZ NOT NULL,
    ip              TEXT NOT NULL DEFAULT '',
    user_agent      TEXT NOT NULL DEFAULT '' CHECK (length(user_agent) <= 254),
    CONSTRAINT auth_sessions_idle_chk CHECK (idle_expires_at <= expires_at)
);
CREATE INDEX ix_auth_sessions_subject ON auth_sessions (realm, subject_id);
CREATE INDEX ix_auth_sessions_expires ON auth_sessions (LEAST(expires_at, idle_expires_at));

CREATE TABLE auth_tokens (
    token_hash  TEXT PRIMARY KEY,
    realm       TEXT NOT NULL CHECK (realm ~ '^[a-z0-9_]{1,32}$'),
    purpose     TEXT NOT NULL CHECK (purpose IN ('verify','reset','email_change')),
    subject_id  UUID NOT NULL,
    payload     TEXT NOT NULL DEFAULT '',      -- новый логин для email_change
    expires_at  TIMESTAMPTZ NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL,
    used_at     TIMESTAMPTZ
);
CREATE INDEX ix_auth_tokens_subject ON auth_tokens (realm, subject_id, purpose);
CREATE INDEX ix_auth_tokens_expires ON auth_tokens (expires_at);

CREATE TABLE auth_login_attempts (
    id         UUID PRIMARY KEY,
    realm      TEXT NOT NULL,
    login_key  TEXT NOT NULL,                  -- нормализованный логин, в том числе несуществующий
    ip         TEXT NOT NULL DEFAULT '',
    at         TIMESTAMPTZ NOT NULL
);
CREATE INDEX ix_auth_login_attempts_key ON auth_login_attempts (realm, login_key, at);
CREATE INDEX ix_auth_login_attempts_at  ON auth_login_attempts (at);
```

HMAC под секретом реалма уже исключает совпадение хэшей между реалмами;
колонка `realm` — вторая линия и ключ уборки. Времена приходят параметром, без
`DEFAULT now()`, иначе тесты на управляемых часах проверяют не то, что пишет
база (ADR-0005).

### `authhttp`: кука и CSRF

`CookieConfig{Name, Secure, SameSite, Path, Domain, CSRFName, CSRFHeader}` с
инвариантами: `SameSite=None` требует `Secure`; имя с префиксом `__Host-`
требует `Secure`, `Path="/"` и пустого `Domain`; заголовок CSRF по умолчанию
`X-CSRF-Token`. `Middleware` достаёт куку, зовёт `Resolve`, кладёт `Principal`
в контекст; на небезопасных методах сверяет CSRF-куку с заголовком
константным по времени сравнением. Сессионная кука — `HttpOnly` всегда,
CSRF-кука — нет (её обязан прочитать фронтенд). Ответы 401 и 403 пишет `Deny`
потребителя через `kit/httperr`: формат ошибки принадлежит его API, а не
пакету.

### Безопасность `auth`

1. **ХЭШ — argon2id PHC С ПОТОЛКАМИ ПРИ ПРОВЕРКЕ.** Параметры лежат в строке
   хэша, поэтому враждебная строка в базе иначе задала бы гигабайт памяти.
2. **ОДИН ГЛОБАЛЬНЫЙ ПОТОЛОК ОДНОВРЕМЕННОСТИ** (2–4 слота на процесс): память —
   свойство одновременности, лимитер по IP её не ограничивает.
3. **ПЕРЕГРУЗКА НЕОТЛИЧИМА.** На `ErrBusy` вход отвечает `ErrTooManyAttempts`
   одинаково для существующего и несуществующего логина — иначе семафор сам
   становится каналом перебора адресов.
4. **ЧЕТЫРЕ МЕХАНИЗМА ПРОТИВ ПЕРЕБОРА:** одна ошибка на «нет логина» и «не тот
   пароль»; холостая проверка (`Equalize`) для неизвестного логина ради
   тайминга; регистрация на занятый адрес отвечает «принято» и шлёт письмо
   владельцу адреса; повторная отправка и сброс — тихий no-op. Счётчик
   блокировки ведётся по нормализованному логину независимо от его
   существования.
5. **ТОКЕНЫ НЕ ХРАНЯТСЯ.** В базе только HMAC под секретом реалма: дамп базы не
   даёт ни живой сессии, ни ссылки сброса. Сырой токен не логируется и не
   попадает в событие аудита.
6. **ОДНОРАЗОВОСТЬ АТОМАРНА.** `Consume` гасит токен и применяет эффект одной
   транзакцией; `Issue` гасит прежние того же назначения; смена пароля
   отзывает все сессии и все токены сброса.
7. **СЕССИЯ СКОЛЬЗЯЩАЯ, НО С ПОТОЛКОМ.** `IdleTTL` продлевается не чаще
   `RenewEvery`, `SessionTTL` абсолютен; отключённый субъект отвергается сразу,
   не дожидаясь истечения.
8. **КУКА HttpOnly ВСЕГДА, CSRF — DOUBLE-SUBMIT** с константным сравнением на
   небезопасных методах; `SameSite` обязателен, префикс `__Host-` проверяется.
9. **ДЛИНА ПАРОЛЯ ПРОВЕРЯЕТСЯ ДО ХЭША** (`MaxPasswordLength` = 1024) — иначе
   мегабайтный пароль это отказ в обслуживании; оценка стойкости — по префиксу;
   правил состава символов нет осознанно (NIST 800-63B). `Checker` обязателен:
   «только длина» — это подмена порта, а не флаг конфигурации.
10. **РЕАЛМЫ РАЗДЕЛЕНЫ.** Разные секреты, куки и источники личностей; общий
    только `Hasher` — ради общего потолка памяти.

### Чего нет в `auth`

TOTP и вторых факторов, passkeys, OAuth и входа через соцсети, JWT, bearer- и
refresh-токенов, API-ключей, «запомнить меня» сверх `IdleTTL`, управления
устройствами, таблицы пользователей, ролей (это `authz`), отправки писем (порт
`Notifier` и `Tokens.Issue` ведут в `mail`), ограничителя частоты запросов
(`kit/ratelimit` снаружи), HTTP-форм входа. Шов для второго фактора оставлен:
`SignIn` возвращает результат, а не только токен. Вход по одноразовому коду —
кандидат в v0.2, если магазину понадобится вход по телефону.

## `authz`: роли, разрешения, реестр операций

```go
type Subject struct { Realm, ID string }
type Role string; type Permission string; type Operation string

type Config struct {                                   // закрытые наборы
    Permissions []Permission
    Roles       map[Role][]Permission
    Inherits    map[Role][]Role                        // циклы — паника конструктора
}
type RoleSource interface { RolesOf(ctx context.Context, s Subject) ([]Role, error) }   // у потребителя
type Policy func(ctx context.Context, s Subject, p Permission, r Resource) (allow bool, err error)

func New(src RoleSource, cfg Config, policy Policy) *Authorizer
func (a *Authorizer) Can(ctx context.Context, s Subject, p Permission) (Decision, error)
func (a *Authorizer) CanOn(ctx context.Context, s Subject, p Permission, r Resource) (Decision, error)
func (a *Authorizer) CanOp(ctx context.Context, s Subject, op Operation) (Decision, error)

type Rule struct { Permission Permission; Public bool; Why string }
func NewRegistry(cfg Config, rules map[Operation]Rule) *Registry   // паника: Public без Why; неизвестное разрешение
```

Хранилища ролей в пакете нет: у одного потребителя роль — колонка в таблице
пользователей, у другого — таблица членства в организации, у третьего она
приходит из внешнего каталога. Всё это — реализация `RoleSource` в двадцать
строк, а таблица в пакете стала бы четвёртым вариантом, который никому не
подходит.

**Реестр операций** — приём, ради которого пакет и заводится. Каждая операция
API объявлена: либо требует разрешения, либо публична **с объяснением, почему**.
Отсутствие правила — отказ. `authztest.RequireAllClassified(t, ops, reg)` берёт
список операций (из сгенерированного интерфейса или из роутера) и роняет тест
на первой неклассифицированной: забытая проверка перестаёт выглядеть как
обычный хендлер.

**`Policy` только сужает.** Хук получает субъект, разрешение и ресурс и может
ответить «нет» там, где RBAC сказал «да»; ответить «да» там, где RBAC сказал
«нет», он не может по конструкции. Баг в хуке ограничен потерей доступа, а не
раздачей прав. Это же и точка подключения `entitlement`: роль даёт разрешение
«читать материал», а `Policy` спрашивает у `entitlement`, куплен ли конкретный
материал.

**`Decision.Reason`** — закрытый набор (`allow`, `deny_no_subject`,
`deny_no_role`, `deny_no_permission`, `deny_policy`, `deny_unclassified`,
`error`), спроектированный как метка метрики: по нему видно, отказ это правило
или сбой. Сбой источника ролей — `ErrUnavailable` и 503, а не 403.

### Безопасность `authz`

1. **DEFAULT DENY.** Операция без правила и субъект без ролей — отказ; реестр
   стережёт инвариант-тест на полном списке операций.
2. **FAIL CLOSED С ЧЕСТНЫМ СТАТУСОМ.** Сбой источника ролей даёт 503, а не
   403: «у вас нет прав» во время недоступной базы — ложь клиенту и утопленный
   инцидент.
3. **POLICY ТОЛЬКО СУЖАЕТ** — баг в хуке не может раздать права.
4. **ЗАКРЫТЫЕ НАБОРЫ.** Неизвестное разрешение в проверке — ошибка
   программиста (отказ и `ErrUnknownPermission`), а не молчаливое «нет».
5. **ЦИКЛЫ НАСЛЕДОВАНИЯ ЛОВЯТСЯ В КОНСТРУКТОРЕ**, и порядок ролей задаётся
   явным `Inherits`, а не порядком объявления констант.
6. **`Public` ТРЕБУЕТ `Why`.** «Открыл и забыл» не проходит молча: обоснование
   лежит рядом с правилом и читается на ревью.
7. **РОЛИ ЧИТАЮТСЯ НА КАЖДУЮ ПРОВЕРКУ.** Отзыв роли действует немедленно; кэш —
   решение потребителя внутри `RoleSource`, с его явным TTL и его риском.
8. **МЕТКИ БЕЗ ИДЕНТИФИКАТОРОВ.** Субъект и ресурс в метрики не попадают —
   только `result` и `Reason`; кто именно и над чем — в аудит потребителя.

### Чего нет в `authz`

Хранения политик, кэша ролей, wildcard-разрешений, разделения по арендаторам,
управления ролями (API и UI — у потребителя), прав на конкретные объекты (это
`entitlement`), casbin и OpenFGA в ядре. Наблюдаемость (`authzotel` со
счётчиком `authz.checks{result,reason}`) — v0.2; `Reason` спроектирован
закрытым уже сейчас именно ради этого.

## `entitlement`: что открыто по покупке

Переезжает целиком, с переименованиями, которые убирают из него предметную
область первого потребителя: `Pack → Product`, `Trainer → Item`,
`User → Subject`. Страж импортов переводится с чёрного списка на белый.

Что остаётся неизменным и составляет ценность пакета:

- **default-deny**: нет записи о выдаче — нет доступа; нулевое значение это
  отказ;
- **fail-closed с честным статусом**: сбой хранилища даёт `ErrUnavailable`
  (503), а не `ErrDenied` (403) — то же правило, что в `authz`;
- **снимок прав с дедлайном** `min(TTL, ближайший expires_at)`: кэш не может
  пережить истечение права, поэтому доступ не «залипает» после окончания
  оплаченного срока;
- **одна загрузка на волну параллельных запросов** (объединение одинаковых
  запросов): вход в популярный материал не превращается в шторм к базе.

Порт `Store{Open(ctx, subjectID, now) ([]Grant, error); Grant; Revoke}`,
`Grant{ItemID, ExpiresAt *time.Time}`. Кэш и объединение запросов пишутся на
stdlib (~150 строк) — по правилу «ядро без внешних зависимостей»; если это
окажется дороже дня работы, откат — известные библиотеки в белом списке с
записанной причиной.

pg-адаптера в v0.1 нет: у первого потребителя свой уже есть, магазину пакет к
старту не нужен. Эталонная схема (`entitlement_products`,
`entitlement_product_items`, `entitlement_grants`) лежит в `doc.go` — по ней
адаптер пишется за полдня, когда понадобится.

## Fail-closed по трём осям

| Ситуация | Fail-open (как бывает) | Fail-closed (пакеты) |
|---|---|---|
| Неизвестный логин на входе | «пользователь не найден» — адрес подтверждён перебором | одна ошибка на оба случая плюс холостая проверка ради тайминга |
| Хэшер перегружен | 500 или отличимый ответ | `ErrTooManyAttempts` одинаково для всех |
| Регистрация на занятый адрес | «адрес занят» | «принято» и письмо владельцу адреса |
| Дамп базы | сессии и ссылки сброса угоняются как есть | в базе только HMAC под секретом реалма |
| Смена пароля | старые сессии продолжают жить | отзыв всех сессий и токенов сброса |
| Операция без правила в реестре | доступна по умолчанию | отказ; инвариант-тест роняет сборку |
| Публичная операция | флаг в коде без следа | `Public` требует `Why` |
| Источник ролей недоступен | 403 «нет прав», инцидент утоплен | `ErrUnavailable` → 503 |
| Хук политики с ошибкой | может расширить права | `Policy` только сужает |
| Право истекло, кэш свежий | доступ живёт до конца TTL | дедлайн снимка не переживает `expires_at` |
| Хранилище прав недоступно | отдаётся «разрешено» из старого снимка | `ErrUnavailable` → 503 |

## Двойники

`authtest`: `MemIdentities`, `MemSessions`, `MemAttempts`, `MemTokens`
(связан с `MemIdentities` и честно применяет эффект назначения токена — иначе
тест «подтверждение адреса» был бы зелёным при неработающем подтверждении),
`RecordingNotifier`, `RecordingAuditor`, `Strength`, `FastHasher` (полы OWASP —
около тридцати миллисекунд на хэш, чтобы тесты шли за секунды), `Clock`.

`authztest`: `MemRoles`, `RequireAllClassified`, `RequireNoDeadRules` (правило
на операцию, которой больше нет, — тоже дефект). `entitlementtest`: двойник
хранилища с управляемыми ошибками и часами.

## Альтернативы

**Три модуля вместо одного `auth`.** Отклонено: `password`, `session` и
адаптеры делят `Realm`, `Principal` и `Identity`; три `go.mod`, три тега и три
строки матрицы CI ради шести общих типов не покупают ничего. Внешние
зависимости у пакетов разные, но каждая заперта в своём подпакете — этого
достаточно (ADR-0005: модуль по семейству, а не по слою).

**JWT и refresh-токены.** Отклонены: у сессии в куке роль refresh играет
скользящее продление, а плата за JWT — невозможность мгновенного отзыва.
Непрозрачная сессия отзывается одним `DELETE`; выход со всех устройств и
принудительный отзыв при смене пароля — обязательные сценарии, и с JWT они
требуют списка отозванных, то есть той же таблицы, ради которой JWT и
отменяли. Пакет не строит API для сторонних клиентов, где JWT оправдан.

**casbin или OpenFGA в ядре.** Отклонены: обе приносят свою модель хранения
политик и свой язык; нужно же — роли, наследование и реестр операций, это
около двухсот строк. Обе остаются допустимыми адаптерами за портом: `Policy`
подключает внешний движок в тот день, когда появятся права по отношениям
(«владелец документа», «участник организации»).

**Слияние `entitlement` в `authz`.** Отклонено: разные оси и разные сроки
жизни ответа. Роль отзывается мгновенно и читается на каждую проверку; право
по покупке живёт до даты и кэшируется. Слияние притащило бы кэш и даты в
проверку ролей и сделало бы отзыв роли медленным.

**Готовый менеджер сессий как ядро.** Отклонён по правилу ADR-0005: ядро —
stdlib плюс `uuid`; подобная библиотека остаётся возможным адаптером порта
`Sessions`, если у кого-то появится хранилище, которого у нас нет.

## Решено с владельцем (2026-09-07)

1. `auth` — один модуль, реалм = экземпляр `session.Service` — да.
2. Сессии непрозрачные, скользящий `IdleTTL` плюс абсолютный `SessionTTL`;
   refresh и JWT не заводим — да.
3. Ролей в `auth` нет; они в `authz` — да.
4. RBAC свой, минимальный: роли, наследование, реестр операций, `Policy`
   только сужает; casbin — только адаптер, если появится ReBAC — да.
5. `entitlement` остаётся отдельным пакетом, `authz.Policy` — точка
   подключения; переименования `Pack → Product`, `User → Subject` — да.
6. `Tokens` реализует потребитель, пакет даёт половину на `Querier` — да.
7. Кэш `entitlement` пишется на stdlib; откат к известным библиотекам
   допустим с записью причины в белом списке — да.

## Последствия

Плюсы: три вопроса разъехались по трём пакетам и не мешают друг другу — отзыв
роли мгновенен, покупка кэшируется, сессия отзывается одним удалением; забытая
проверка прав роняет тест, а не обнаруживается на проде; два реалма работают в
одном процессе без второго экземпляра кода; таблица пользователей остаётся у
потребителя со всеми его связями.

Минусы, принятые осознанно: потребитель обязан написать три небольших адаптера
(`Identities`, `Tokens`, `RoleSource`) — это цена того, что его таблицы
остаются его; без готовой таблицы ролей первый потребитель пишет свои двадцать
строк; вторых факторов нет, и если они понадобятся раньше v0.2, это отдельная
работа, а не флаг; `entitlement` в v0.1 идёт без pg-адаптера.
