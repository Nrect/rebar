# Дорожная карта: от одного пакета к тулкиту

Дата плана: 2026-09-07. Состояние обновляется по мере выпуска модулей.

## Зачем

Тулкит нужен там, где один человек ведёт много проектов. Переносимые блоки —
почта, платежи, очередь событий, доступ, наблюдаемость — живут в одном месте,
тестируются один раз и чинятся от уязвимостей один раз; проекты подтягивают
новую версию, а не копируют каталог заново.

Проверено на живом примере: два проекта-потребителя держали по копии одних и
тех же внутренних пакетов, и копии разъехались. В одной зрелее защита от
перебора и ограничение одновременных хэширований, в другой — правильная форма
(страж импортов, двойники, управляемые часы). Уязвимость в такой конфигурации
чинится дважды, а инвариант, найденный в одном проекте, во второй не приезжает
никогда.

Ближайшая цель — фундамент, на котором соберётся третий потребитель:
интернет-магазин примерно на 10 000 SKU. Доменные блоки магазина (каталог,
корзина, заказ) проектируются на живом коде и извлекаются в тулкит потом, а не
наоборот.

## Принципы упаковки

Коротко; полностью и с причинами — [ADR-0005](adr/0005-packaging.md).

- **модуль на пакет**, тег `<pkg>/vX.Y.Z`; единственное исключение — `kit`,
  многопакетный модуль без внешних зависимостей вовсе;
- **внешняя библиотека — только в адаптере**, подпакетом, по одной на причину;
  ядро — stdlib плюс `uuid`;
- **межмодульных зависимостей ровно две**: на `kit` и на `postgres/pgtest` из
  тестов. Всё остальное связывается структурно — совпадением сигнатуры
  `Run(ctx) (int, error)` и методами классификации ошибок, а не общими типами;
- **единая версия Go и общих библиотек** во всех модулях, проверяется в CI;
- **`schema.sql` адаптера — часть контракта**: потребитель копирует её в свои
  миграции, поэтому имена ограничений и индексов ломать нельзя;
- **копируемые мелочи не выносятся в общий пакет до третьего потребителя;**
- **гейты не заходят в рабочие каталоги веток** (`.claude/worktrees` исключён в
  Makefile, скриптах и поиске модулей CI): там лежат незавершённые ветки, и
  общий прогон падал бы на чужой работе.

## Решения по спорным вопросам

| Вопрос | Решение | Где подробно |
|---|---|---|
| общая очередь и почта | `mail` автономен навсегда; общий `outbox` рядом по той же форме — инварианты конфликтуют на уровне схемы | [ADR-0002](adr/0002-outbox.md) |
| отдельный пакет заданий | не заводится: разовое и отложенное задание — сообщение с `NotBefore`, периодика — `scheduler`; готовый планировщик заданий остаётся возможным адаптером с записанными триггерами пересмотра | [ADR-0002](adr/0002-outbox.md) |
| `auth` одним модулем или тремя | один модуль; реалм — экземпляр сервиса со своим секретом и кукой; сессии непрозрачные, refresh и JWT не заводим | [ADR-0003](adr/0003-auth-authz-entitlement.md) |
| роли | свой минимальный RBAC: роли, наследование, реестр операций с default-deny, хук политики, который только сужает; внешние движки — адаптеры при появлении прав по отношениям | [ADR-0003](adr/0003-auth-authz-entitlement.md) |
| права на объект по покупке | `entitlement` остаётся отдельной осью; точка подключения — хук политики `authz` | [ADR-0003](adr/0003-auth-authz-entitlement.md) |
| мелочь (ошибки, конфиг, секреты, лимитер, повторы) | один модуль `kit`, stdlib-only | [ADR-0005](adr/0005-packaging.md) |
| транзакции и тестовая база | один модуль `postgres`: пакет транзакций плюс `pgtest`, который всё равно попадает в граф каждого адаптера через тесты | [ADR-0005](adr/0005-packaging.md) |
| шифрование значений | сразу с заголовком блоба (версия и идентификатор ключа) и связкой ключей; ротация — перешифрование | `kit/secrets` doc.go |
| ограничитель частоты | свой token bucket на stdlib, без фоновой горутины: уборка — задача планировщика | `kit/ratelimit` doc.go |
| конфигурация | маленький загрузчик с типизированными читателями и всеми ошибками списком; тип секрета редактируется в выводе | `kit/config` doc.go |
| inbox, распределённая блокировка, сага, SMS, персональные данные | v0.2: inbox — пока паттерн, блокировка — при втором экземпляре сервиса, сага — при втором потребителе | [ADR-0002](adr/0002-outbox.md), [docs/PATTERNS.md](PATTERNS.md) |
| платёжный провайдер | порт один, адаптер пишется, когда провайдер выбран; провайдер без подписи уведомлений меняет инвариант на «источник правды — API провайдера» | [ADR-0004](adr/0004-payment.md) |

## Карта модулей

Состояние на 2026-09-14. «К старту магазина» — нужен ли модуль к запуску
третьего потребителя. «Ждёт тега» означает, что работа слита в `main` и
проходит гейты, а номер выпуска ставится одним заходом после волны
[ADR-0007](adr/0007-error-kind.md): иначе потребитель обновляется на ломающее
трижды подряд вместо одного раза.

| Модуль | Пакеты | Внешние зависимости (только в адаптерах) | К старту магазина | Состояние |
|---|---|---|---|---|
| `kit` | `errs`, `errs/httperr`, `errs/errstest`, `config`, `secrets`, `ratelimit`, `ratelimithttp`, `retry`, `reqid` | нет вовсе | да | **`kit/v0.2.0`** |
| `postgres` | `postgres`, `pgtest`, `pglock` | pgx/v5; testcontainers и goose — только в `pgtest` | да | **`postgres/v0.2.0`** |
| `scheduler` | `scheduler`, `schedulerotel`, `schedulertest` | otel/metric — только в `schedulerotel` | да | `v0.1.0`, ждёт тега |
| `otelboot` | `otelboot`, `errtrack` | otel sdk, prometheus; sentry-совместимый трекер — в `errtrack` | да | **`otelboot/v0.1.0`** |
| `mail` | ядро, `smtp`, `sesv2`, `mailpg`, `mailotel`, `mailtest`, `cmd/sesfake` | go-mail, pgx, otel | да | `v0.2.0`, ждёт тега |
| `outbox` | `outbox`, `outboxpg`, `outboxotel`, `outboxtest` | pgx, otel | да | `v0.1.0`, ждёт тега |
| `payment` | `payment`, `prorate`, `paymentpg`, `paymentotel`, `paymenttest`, `cmd/psfake` | pgx, otel | да | `v0.2.0`; **адаптера провайдера нет** — деньги не принимаются |
| `auth` | `auth`, `loginid`, `password`, `pwzxcvbn`, `session`, `token`, `authpg`, `authhttp`, `authtest` | x/crypto, оценщик паролей, pgx | да | `v0.1.0`, ждёт тега |
| `authz` | `authz`, `authzhttp`, `authzpg`, `authztest` | pgx — только в `authzpg` | да | **`authz/v0.1.0`** |
| `entitlement` | `entitlement`, `entitlementpg`, `entitlementtest` | pgx — только в `entitlementpg` | нет | `v0.1.0`, ждёт тега |
| `objectstore` | `objectstore`, `s3`, `imgproxy`, `fs`, `objectstoretest` | подпись запросов на stdlib | нет (приходит вместе с каталогом) | `v0.1.0`, ждёт тега |
| `audit` | `audit`, `auditpg`, `auditotel`, `audittest` | pgx, otel | желательно | `v0.1.0`, ждёт тега |
| `examples/monolith` | модуль с `replace` на соседей | все | да (гейт тегов) | **собирается и гоняется**; версий не получает |

Ограничения, которые стоит знать до выбора модуля, — раздел «Признанные
долги» ниже. Коротко: адаптера платёжного провайдера нет; `entitlement`
получил `entitlementpg` только 2026-09-14; неидемпотентная периодика требует
`postgres/pglock`, иначе тулкит рассчитан на один экземпляр сервиса.

Спецификации модулей здесь не дублируются — они в ADR:
[ADR-0001](adr/0001-mail.md) (`mail`), [ADR-0002](adr/0002-outbox.md)
(`outbox` и сага на нём), [ADR-0003](adr/0003-auth-authz-entitlement.md)
(`auth`, `authz`, `entitlement`), [ADR-0004](adr/0004-payment.md) (`payment`),
[ADR-0005](adr/0005-packaging.md) (упаковка, процесс, критерии готовности),
[ADR-0006](adr/0006-objectstore.md) (`objectstore`),
[ADR-0007](adr/0007-error-kind.md) (класс ошибки знает пакет, слаг —
потребитель), [ADR-0008](adr/0008-pglock.md) (распределённая блокировка
декоратором прогона), [ADR-0009](adr/0009-ledger.md) (`ledger` — журнал
движений с материализованным остатком). Модули без ADR объясняют себя
в `doc.go`.

## Доменные пакеты магазина: извлекаются с живого кода

Они не пишутся заранее. Каждый ждёт своего триггера: до него код живёт у
потребителя, после — переезжает в тулкит вместе с тестами.

| Пакет | Что | Триггер извлечения |
|---|---|---|
| `pricing` | цены, скидки, распределение суммы без потери копейки, НДС, котировка с дайджестом | чистая логика — можно сразу после старта |
| `inventory` | остатки и резерв с TTL, неотрицательность под блокировкой, движения append-only | заказ прожил две недели |
| `order` | идемпотентный checkout, снимок цен, машина статусов, возвраты по позициям, события в очередь | форма устоялась на живом магазине |
| `cart`, `promo` | корзина гостя и аккаунта со слиянием; коды и правила с лимитами | вместе с `order` |
| `address` | структурный адрес и подсказки | до расчёта доставки |
| `delivery` | порт перевозчика: котировка, накладная, отслеживание, разбор уведомлений, пункты выдачи | договор с перевозчиком у потребителя |
| `search` | полнотекстовый поиск на Postgres и фасеты по белому списку | каталог наполнен |
| `catalog` | только инвариантная часть: товар → варианты (артикул неизменяем), опции, атрибуты со схемой, категории, галерея | второй потребитель каталога |
| `importkit` | потоковый разбор CSV и XLSX по схеме, лимиты, отчёт, сухой прогон, защита от инъекций в таблицах | нужен к наполнению каталога |
| `feed`, `sms`, `pii` | товарные выгрузки и карта сайта; SMS с дневным потолком; согласия и обезличивание | по потребности |

Что магазину нужно от соглашений сразу — уже записано:
[CONVENTIONS §10](../CONVENTIONS.md) (деньги целыми минорными, `WithTx` у
каждого pg-адаптера, `Run(ctx) (int, error)` у каждого фонового метода,
закрытые перечисления зеркалятся CHECK).

## Чего не делаем

Брокеров сообщений и очередей на Redis (транзакционный outbox нужен всё равно);
кэша и лимитера на Redis до второго экземпляра сервиса; своего раннера
миграций и автомиграций из библиотеки; CMS, админ-UI, шаблонов и локализации;
ORM и кодогенераторов внутри тулкита; движков workflow и готовых планировщиков
заданий в ядре; движков политик в ядре; отдельного поискового сервиса, пока
хватает Postgres; обработки изображений внутри процесса; SDK провайдеров;
публикации docker-образов (фейки собираются из `cmd/`); платных сервисов там,
где хватает бесплатных; адаптеров на `database/sql`; мультивалютности и
рекуррентных платежей до живого запроса; доменных пакетов магазина до живого
кода.

Каждый пункт — решение с причиной, а не пробел. Триггеры пересмотра записаны в
«Чего нет» соответствующих пакетов.

## Календарь

**Неделя 0 — правила и документы.** Приёмка и тег `mail/v0.1.0`; ADR-0002…0005;
[CHIP.md](CHIP.md) (шаблон задания исполнителю), [CORRECTNESS.md](CORRECTNESS.md)
(хартия корректности: append-only, идемпотентность, база как арбитр, CAS-статусы,
снимок вместо ссылки, сверка), [PATTERNS.md](PATTERNS.md) (клиент внешнего API,
`decide → effect → commit`, композиция `WithTx`, inbox); правки соглашений,
версионирования, CI и Makefile. **Сделано.**

**Недели 1–4 — фундамент.** `postgres` и `pgtest` первыми (без них не собрать
ни один pg-адаптер), затем `scheduler`, `kit`, `otelboot`, `outbox`, `payment`,
`auth`, `authz`, по необходимости `audit`, `objectstore`, `entitlement`.
Завершается сборкой `examples/monolith` и тегами `v0.1.0`. В основную ветку
влиты `postgres`, `scheduler`, `kit`, `otelboot` и ядро `outbox`; репозиторий
на `go 1.26.0`. Идут адаптеры очереди и ядро `payment`.

Линия отсечения, если месяц не сходится: сначала `postgres`, `kit`,
`scheduler`, `outbox`, `payment` (с фейком провайдера); затем `auth`, `authz`,
`otelboot`; в последнюю очередь `objectstore`, `audit`, `entitlement` и
наблюдаемость платежей. Магазин первые недели может жить с гостевым checkout.

**Недели 5–8 — магазин строится, тулкит отвечает на запросы живого
потребителя.** `pricing`, `importkit` для наполнения каталога, inbox для
уведомлений о доставке, распределённая блокировка (если появится второй
экземпляр сервиса), почта v0.2, вход по одноразовому коду (если понадобится
вход по телефону), второй адаптер провайдера по требованию. Параллельно первый
потребитель переезжает на `mail` и `scheduler` — это первое доказательство
переносимости не на бумаге.

**Недели 9–12 — сбор урожая.** `inventory`, `order`, `delivery`, `address`,
`search` извлекаются из живого магазина. Остальные проекты-потребители
переводятся на `kit`, `scheduler`, `postgres`. Первый кандидат на выход из 0.x —
`scheduler`: у него два потребителя и простой порт.

## Признанные долги

Список того, что решено сделать позже осознанно, а не забыто.

| Долг | Почему сейчас нельзя | Когда |
|---|---|---|
| Разбор «база отбила запись ИМЕНОВАННЫМ ограничением» живёт копиями в `paymentpg` (`raisedBy`) и понадобится каждому адаптеру с триггерами | `postgres.IsUniqueViolation` закрывает только 23505, то есть индексы; инварианты, которые держат триггеры, приезжают как 23514 с тем же полем имени. Потребителей пока два — правило «не выносим до третьего» ещё не сработало | при третьем: `postgres.IsCheckViolation(err, constraint)`, работающий и до `Sanitize`, и после |
| Подпись SigV4 живёт двумя копиями: `mail/sesv2` и `objectstore/s3` | межмодульные зависимости ограничены `kit`, `postgres` и `postgres/pgtest` (ADR-0005); тянуть модуль почты ради подписи нельзя, а правило «копируемые мелочи не выносятся до третьего потребителя» ещё не сработало — потребителей два | при третьем: приём уезжает в общий пакет вместе с векторами из документации AWS, по которым обе копии сейчас и проверяются |
| Доменные sentinel-ошибки (`payment.ErrUnsupported`, `ErrProviderRejected` и соседи) не несут HTTP-класса: каждый потребитель сопоставляет их своей таблицей руками, и класс без правила молча становится умолчанием — 500. Вскрылось на `payment/v0.2.0`: снятие обёртки `ErrUnavailable` с окончательных отказов превратило бы нынешние 503 в 500 у всякого, кто правила на `ErrUnsupported` не завёл | «формат ошибки принадлежит потребителю» (`kit/errs/httperr`, `Translate`) — решение верное для ФОРМАТА, но КЛАСС (повторяемо или окончательно) знает пакет, а не потребитель; развести одно и другое — изменение нескольких модулей сразу, не правка на ходу | **ЗАКРЫВАЕТСЯ 2026-09-14** решением [ADR-0007](adr/0007-error-kind.md): класс объявляет пакет (`errs.KindError`, зависимость на `kit` разрешена отовсюду, ADR-0005), слаг остаётся за потребителем, `httperr` без правила отдаёт статус класса и слаг по имени класса вместо 500 |
| Причина закрытия попытки оплаты не хранится в намерении: статус `failed` один на оба окончательных класса, поэтому повтор по попытке, закрытой из-за `ErrUnsupported`, отдаёт `provider_rejected`, а не `unsupported`. Потребитель с правилами 501/409 увидит 501, а на повторе 409 | класс ответа верный на обоих путях — окончательный отказ, без ретрая; деградирует только метка разбора («кто чинит»: интеграция или поддержка). Лечение — колонка с CHECK в `paymentpg`, поле в `Intent`, двойник, контрактный набор, `CheckSchema`, то есть миграция схемы выпущенного адаптера без потребителя, которому это мешает | когда потребителю понадобится различать эти два отказа на повторе; закреплено тестом и строкой в CHANGELOG `payment` |
| У `pglock` нет `*otel`-декоратора, хотя он есть у `mail`, `outbox`, `payment`, `audit` и `scheduler`. Пример-монолит написал свой (`examples/monolith/lockotel`, ~60 строк: счётчик `cron_lock{job,result}` с предрегистрацией нулями) — следующий потребитель напишет такой же | стоимость не в коде, а в графе: `postgres` сегодня otel в коде НЕ импортирует (в `go.mod` он только `// indirect`, приезжает с testcontainers). Подпакет сделает его прямой зависимостью модуля, который пинят шесть модулей, включая `entitlement`, у которого otel нет вовсе. Цена мала — otel уже в `go.sum` — но это ровно то решение, которое ADR-0005 велит принимать вслух | вместе с `authzotel` и `entitlementotel`: у всех трёх один повод и одна цена, и разбирать их по одному значит трижды обсуждать одно |
| Префикс пакета в тексте sentinel'а держится тестом каждого модуля (`TestSentinelKinds`), а не стражем `errstest.EveryErrorHasKind`. Тест, написанный руками в восьми модулях, — восемь способов написать его так, что он не сработает | страж уже обходит исходники и знает имя пакета из `package …`, так что проверка текста на префикс укладывается в него целиком. Но это `kit/v0.3.0` посреди волны и перепин в каждом модуле, который уже взял `v0.2.0`; правило при этом известно и записано в [ADR-0007](adr/0007-error-kind.md) | после волны, одним заходом вместе с бампом `kit`: тогда перепин делается один раз и всем сразу |
| Двойники `mailtest`, `outboxtest`, `objectstoretest` и `audittest` отдают моменты так, как их передали, а их pg-адаптеры — как круг через `timestamptz`: в UTC и с точностью до микросекунд. Потребитель, сравнивающий метку времени, зелен на двойнике и красен в проде. Проверено перебором семи пакетов двойников: `Truncate(time.Microsecond)` есть только у `paymenttest`, `authtest` и `entitlementtest`; у `audittest` нет и `.UTC()` | тот же класс, что «двойник мягче базы», закрытый в `entitlement` ([решение 3](adr/0003-auth-authz-entitlement.md)); лечение то же — двойник усекает и приводит к UTC, сравнение в контрактном наборе переводится с голого `Equal` на сравнение зоны и усечённого момента. Но это четыре модуля с бампом каждому, и каждый из них и так ждёт бампа по волне [ADR-0007](adr/0007-error-kind.md) | той же волной: те же четыре модуля, одно обновление у потребителя вместо двух. Доказательство в каждом — сценарий в `Run*Suite`, падающий у двойника при откате правки |
| `SetClock` существует в двух формах: паникует на `nil` в `auth/session`, `kit/ratelimit` и `scheduler` — просто присваивает в девяти остальных (`mail`, `outbox`, `payment`, `audit`, `entitlement`, `objectstore/collector`, `objectstore/s3`, `authzpg`, `objectstoretest`). Проверено перебором всех тринадцати реализаций | правильна форма с паникой: `SetClock` — это настройка, а настройка у нас падает громко и на старте (CONVENTIONS §2). Девять присваивающих откладывают отказ до вызова часов, где он выглядит разыменованием nil в чужом стеке. Но это правка девяти модулей с бампом каждому, а посреди волны адаптеров и выпуска тегов она стоит дороже, чем ждёт | одной волной вместе с классом ошибки на sentinel'ах ([ADR-0007](adr/0007-error-kind.md)): те же модули, тот же бамп, одно обновление у потребителя вместо двух |

## Критерии готовности пакета к тегу `v0.1.0`

Короткая форма; полные формулировки — [ADR-0005](adr/0005-packaging.md),
чек-лист — [CONVENTIONS §7](../CONVENTIONS.md).

1. `doc.go` со списками «Безопасность:» и «Чего в пакете НЕТ».
2. Страж импортов с белым списком по каждому каталогу.
3. Порты ядра без чужих типов.
4. `<pkg>test` с двойниками всех портов, моделирующими инвариант.
5. `Config` с panic-валидацией, нулевое значение — отказ, `SetClock`.
6. Закрытые перечисления с `All*` и guard-тестом.
7. Тесты из контрактов портов, проверяющие чтением из базы.
8. `schema.sql` с обеими сторонами миграции, применяется на пустую базу.
9. Секреты и тела не попадают в логи, ошибки и метки — есть тест.
10. Мутационный прогон ядра, необъяснённых выживших ноль.
11. `make chip-check MODULE=<модуль>` и `make lockstep` зелёные.
12. Таблица метрик и алертов, `CHANGELOG.md`, строка в «Жителях».
13. `examples/monolith` собирается и проходит smoke с этим модулем.

## Риски

| Риск | Мера |
|---|---|
| ревью становится узким местом при параллельной работе | линия отсечения по приоритетам; магазин стартует с частей, не зависящих от тулкита, и подключает платежи и вход позже |
| платёжный провайдер ещё не выбран | порт, двойник и стенд пишутся сейчас; адаптер — несколько дней после выбора; список сетей и тонкости API живут в конфигурации, а не в коде |
| расползание платежей при обобщении | закрытый список вырезаний в [ADR-0004](adr/0004-payment.md); всё остальное остаётся у первого потребителя |
| тестовая база задерживает адаптеры | модуль `postgres` выпускается первым |
| кэш прав на stdlib съедает больше времени, чем стоит | откат — известные библиотеки в белом списке с записанной причиной |
| пример-монолит устаревает и перестаёт быть гейтом | джоб на основной ветке; пример служит заготовкой точки входа для магазина |
| двойной запуск фоновых задач при втором экземпляре сервиса | идемпотентность прогона — свойство задачи; распределённая блокировка в v0.2 |
| разъезд версий Go и общих библиотек между модулями | джобы `lockstep`, бамп одним PR по всем модулям |
